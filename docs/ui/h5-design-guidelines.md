## 2. 核心决策

| 决策 | 约束 |
|---|---|
| 设计基准 | 430px 宽移动端，最低支持 320px，无水平滚动 |
| 桌面预览 | 大于等于 768px 时以 430px 宽设备容器居中展示，而非拉成平板网页 |
| 视口 | 使用 `100dvh`；禁止把 `100vh` 作为应用高度依据 |
| 导航 | 登录后的目标信息架构为 4 个底部 Tab；认证页、详情页不强制使用底部导航 |
| 组件库 | Tailwind CSS + shadcn/ui Base UI + Lucide；不得引入第二套 UI 库 |
| 配色 | 使用设计稿深森林绿主题，通过统一语义 token 落地，具体值见第 11 节 |
| 深色模式 | 不提供切换入口，但所有新组件只能使用语义 token，为 `.dark` 主题预留空间 |
| 视觉方向 | 可信、克制、清爽、生活化；不做医疗机构风，也不做健身游戏化 |
| 页面重心 | 单列内容、每屏一个主要目标、同一区域只保留一个主操作 |

## 3. 设计方向：可信的饮食健康工具

### 3.1 产品气质

本项目不是医疗诊断产品，也不是通过勋章、排行榜和强刺激色制造焦虑的健身应用。界面应让用户快速完成“提供饮食信息 → 补充分量 → 查看估算 → 确认记录”，视觉为信息和决策服务。

- 使用紧凑页头、短说明、稳定间距和低层级卡片，不堆叠装饰性模块。
- 页面首屏只突出一个主要动作；次要动作使用次级按钮或文本入口。
- 保持适度层次，但不依赖重阴影、玻璃拟态、高饱和渐变或大面积装饰图形。
- 交互文案使用“分析”“估算”“待确认”等准确措辞；禁止用“精准识别”“绝对健康”等无法证明的承诺。
- 图标统一使用 Lucide SVG，不用 Emoji 充当产品图标，也不混用多套图标库。

### 3.2 信息可信度与饮食数据层级

一餐结果页优先按以下层级展示：

1. 总热量估算区间，例如 `650–850 kcal`。
2. 每种食物的具体菜名、克数和热量估算。
3. 需要用户确认或修改的信息，例如菜品识别结果和份量。
4. 碳水、蛋白质、脂肪等补充营养信息。
5. 免责声明与说明。

约束如下：

- 用户输入的份量使用明确克数；未知份量必须标记为估算，不伪装成精确测量。
- 热量、克数和营养数值统一使用 `tabular-nums`；单位紧邻数值，格式全站一致。
- AI 输出与确定性计算结果要在视觉和文案上可区分：AI 负责识别与追问，数值由后端营养工具计算。
- 不用虚假的小数位、百分比或“置信度 99%”制造精确感。
- 营养来源按既定产品决策仅在后端 API 与数据库保留；H5 不增加来源展示入口，但“估算”状态必须对用户透明。
- 错误、警告、待确认和成功状态不能只靠颜色区分，必须同时使用文字或图标。

### 3.3 字体与基础排版

不额外加载远程字体，优先使用系统无衬线字体，降低 H5 首屏成本并保证中文可读性。设计稿加载了 Noto Sans SC（400/500/600/700），这里保留中文无衬线气质，但不强制复制 Google Fonts 请求；若引入字体资源，先验证中文回退、字重和加载性能。

| 层级 | 建议字号/行高 | 用途 |
|---|---|---|
| Tab 页头标题 | 20/20px，700 | 左侧图标后，每页唯一 `h1` |
| 详情页头标题 | 18/24px，600 | 顶栏居中，单行截断 |
| 热量估算区间 | 32/40px，700 | 分析报告首卡 |
| 今日摄入大数值 | 36/44px，700 | 记录页概览 |
| 区块标题 | 15–16/24px，600 | 页面一级内容区 |
| 卡片标题 | 16/24px，600 | 菜品、记录、计划卡片 |
| 正文 | 15/24px，400 | 主要说明与列表内容 |
| 辅助文字 | 13/20px，400 | 时间、状态、补充说明 |
| Tab 标签 | 11–12/16px，500 | 底部导航 |

- 表单输入文字不得小于 16px，避免 iOS 聚焦时自动缩放页面。
- 标题层级必须按 `h1 → h2 → h3` 顺序组织，不能为了字号跳级。
- 长标题最多两行，导航标题单行截断；正文不使用过窄行高。

## 4. 四个 Tab 的目标信息架构

登录后，用户 H5 使用四等分底部导航。名称和职责如下：

| 顺序 | Tab / 页头 | Lucide 图标 | 设计稿路由 | 内容职责 |
|---|---|---|---|---|
| 1 | 分析 / 分析这餐 | `ScanLine` | `/analyze` | 文字/图片输入、追问、营养估算与保存 |
| 2 | 记录 / 饮食记录 | `NotebookText` | `/records` | 今日摄入、趋势、历史与周复盘 |
| 3 | 计划 / 饮食计划 | `CalendarDays` | `/plan` | 资料摘要、偏好确认、生成餐单与历史 |
| 4 | 我的 / 我的 | `UserRound` | `/profile` | 账号摘要、资料目标、会话与偏好 |

路由列用于设计映射；落地时结合本项目现有路由与认证守卫，不因换肤破坏已有链接。页面能力以当前路由、公开 API 与真实实现为准。尚未开放的能力只显示标题与“功能即将开放”，不得用示例数据或模拟操作冒充真实能力。

### 4.1 四页内容顺序

- **分析**：输入卡（拍照主按钮、相册描边按钮，或文字输入）→ 切换输入模式 → 开始分析 → 五步进度 → 估算总热量 → 食物明细 → 修正/排除 → 营养素构成 → 忌口提示 → 餐次与可选用餐时间 → 确认并保存 → 删除本次分析。图片预览为 4:3；保留源输入供核对。五步显示“感知餐食、等待补充、营养计算、结果校验、完成分析”，由真实流程驱动，等待补充时提供可操作的追问区域。
- **记录**：今日已记录摄入与餐数 → 营养目标状态 → 近七日能量折线图与日期/能量/餐数表 → 按日期分组的历史记录（展开菜品）→ 周复盘。图表不能替代数值表；数据不足时展示真实提示。
- **计划**：普通饮食参考提示 → 身体资料与目标摘要（或缺失提示与“去填写”）→ 历史计划入口 → 本次饮食偏好与管理入口 → 复核偏好复选框 → 生成按钮 → 餐单结果。资料摘要首行四格为身高/体重/年龄/性别，次行两格为活动水平/饮食目标。编辑统一进入个人资料页，不在计划页重复完整资料表单。
- **我的**：头像、姓名、邮箱及账号状态/角色摘要 → 个人资料与目标、登录会话、饮食偏好与记忆入口 → 当前目标与忌口摘要 → 退出登录 → 版本信息。账号和版本必须来自真实状态。

以下以设计稿可见结构为基准；涉及保存、恢复、校验与权限的行为是生产实现要求，不能以原型按钮存在作为能力已交付的证据。

| 区域 | 设计稿结构 | 生产实现要求 |
|---|---|---|

| 偏好详情 | 忌口、口味偏好、过敏原三组标签；查看态与编辑态分离 | 编辑使用草稿；取消不写入，保存失败不退出编辑；分类须服从服务端白名单，不能扩大长期记忆范围 |
| 登录会话 | 当前设备强调卡、其他设备列表与撤销确认 | 设备和活跃时间来自真实会话；缺少位置数据时不编造城市，撤销失败保留列表并提示重试 |

## 5. 页面壳：不要用一个布局硬套全部页面

后续实现必须以一层设备容器和三个明确的布局边界组织，而不是让 `body`、页面内容和底部导航同时滚动。

```text
浏览器视口
└─ MobileFrame
   ├─ PublicAuthLayout（公开页/认证页）
   ├─ AppShell（登录后 Tab 根页面）
   │  ├─ AppHeader（固定页头）
   │  ├─ PageScrollArea（唯一纵向滚动区域）
   │  └─ BottomNavigation（4 项）
   └─ DetailLayout（返回顶栏 + 内容区 + 可选固定操作栏）
```

### `MobileFrame`

- 手机端：占满可用视口，不显示设备边框、阴影或外层圆角。
- `min-width: 768px`：宽度为 `min(430px, calc(100vw - 2rem))`，高度为 `calc(100dvh - 2rem)`，居中，使用 32px 圆角、1px 弱边框和单层柔和阴影。
- 容器本身使用 `display: flex`、`flex-direction: column`、`overflow: hidden`。不让浏览器 `body` 和页面内容双重滚动。
- 使用 `100dvh` 适配移动浏览器地址栏变化；`100svh` 只可作兼容性回退，不是主高度。

### `PublicAuthLayout`

用于首页、登录、注册、验证码、找回密码、隐私和条款：

- 没有底部 Tab。
- 只有一个可滚动内容区；内容短时允许垂直居中，内容长时自然滚动。
- 表单页面可以有返回按钮，但不伪造业务顶部导航。
- 认证页不得被未来的 AppShell 底部导航包裹。

公开首页的信息顺序保持精简：主标题与一句价值说明 → 一个主要 CTA → 最多三个能力说明 → 登录/隐私等次要入口。不要在首屏同时堆放注册、登录、上传图片和查看示例四个同等级按钮。

### `AppShell`

用于已登录的四个 Tab 根页面：

- 结构固定为“固定顶部栏 + 唯一内容滚动区 + 固定底部导航”。
- 外层 `overflow: hidden`；内容区必须有 `flex: 1`、`min-height: 0`、`overflow-y: auto`。
- 顶部栏和底部导航不随内容滚动。
- AppShell 只包裹 Tab 根页面；进入详情、编辑、确认或全屏对话流程时，改用 `DetailLayout`。

### `DetailLayout`

用于有返回动作的详情、编辑、确认和步骤页面：

- 顶部保留返回按钮与标题，标题过长必须截断。
- 内容区仍然只有一个纵向滚动容器。
- 有提交操作时使用固定底部操作栏；此时不与底部 Tab 同时出现。

## 6. 尺寸、间距与安全区

### 间距

以 4px 网格为主。常用值为 `4 / 8 / 12 / 16 / 20 / 24 / 28px`；10px 是设计稿用于图标间隔等紧凑场景的明确例外，不扩展为任意间距。

| 场景 | 规则 |
|---|---|
| Tab 根页内容左右边距 | 28px（设计稿壳层 12px + 页面 16px 的实际效果）；生产由一层管理 |
| 详情页内容左右边距 | 16px |
| 320px 窄屏内容左右边距 | 收至 12–16px，保证表单与数值可读 |
| 内容区顶部间距 | 16px |
| 区块间距 | 12px，详情分组可用 16px |
| 普通卡片内边距 | 16px；紧凑修正/步骤区 12px |
| 标准 CardHeader / CardContent | 24px 水平内边距，正文顶部由标题区衔接；按页面覆盖为 16px |

组件内部使用 `gap`、`flex` 或 `grid` 组织间距；不要靠堆叠随机 `margin` 修出布局。

### 固定区域与触控

| 元素 | 规则 |
|---|---|
| Tab 顶部栏 | 内容高 20px + 上下各 18px，共 56px，另加顶部安全区 |
| 详情顶部栏 | 内容高 24px + 上下各 12px，共 48px，另加顶部安全区；返回命中区 44px |
| 底部导航主体 | 64px，另加底部安全区 |
| 主按钮 | 高 44px，最小点击面积 44×44px |
| 输入框 | 高 44–48px；紧凑小屏可为 40px |
| 次级按钮 | 紧凑小屏可为 32–36px，但关键操作仍保持 44px 命中区 |

底部导航主体 64px 不含安全区；固定提交栏基础上下间距 12px。安全区与主体高度分别计入：

```text
底部导航总高度: calc(64px + env(safe-area-inset-bottom))
底部导航 padding-bottom: env(safe-area-inset-bottom)
固定操作栏 padding-bottom: calc(12px + env(safe-area-inset-bottom))
```

设计稿 Tab 的固定 64px 高度内包含安全区 padding，生产实现需改为上述叠加方式，避免挤压导航。页头、导航与操作栏均占据 flex 布局空间；内容区仅保留正常底部间距，不复制设计稿壳层 `pb-16` 与页面 `pb-24` 叠加产生的 160px 空白。

顶部栏同样预留 `env(safe-area-inset-top)`；不能只考虑 iPhone Home Indicator 而忘记刘海、横屏和动态岛。

## 7. 导航规范

### 顶部栏

- Tab 根页：左对齐 20px 主色图标与 20px 粗体标题，间隔 10px，左右 padding 16px；此图标为装饰，不暗示返回。
- 详情页：左侧返回按钮，18px 标题绝对居中、最大宽度约 60%，右侧为编辑等上下文操作；标题单行截断。图标按钮命中区至少 44×44px，必须有 `aria-label`。
- 左、中、右三部分不得互相挤压。标题优先缩略，返回按钮永远可点击。
- 可以使用轻微背景模糊，但文字和图标的对比度必须足够。

### `BottomNavigation`

- 只用于 `AppShell` 的 4 个根 Tab，四等分布局。
- 每项为“约 22px 图标 + 11–12px 文字”，图标在上、文字在下。
- 当前项只改变语义主色和文字字重/颜色，不用厚重胶囊背景、悬浮大圆按钮或破坏栏高的中央入口。
- 有弱分割线和高不透明度背景；可以轻微模糊背景。
- 导航项的无障碍名称必须包含 Tab 名称与当前状态，例如“分析，当前页面”。
- 导航使用真实路由与浏览器历史；浏览器返回键必须可预测工作，不得用无条件 `location.replace()` 破坏返回路径。
- 横向筛选、标签和分类不是底部导航，使用独立横向滚动区，不折行、不挤压文字。

## 8. 卡片、栅格与内容区

- 全站基础圆角 8px；卡片用 12px（设计稿 `rounded-xl`）；输入、普通按钮和图片预览用 8px；紧凑提示块用 6px；标签才允许 `999px` 胶囊圆角。
- 边框仅 1px、低对比度；普通卡片可用统一 `shadow-sm`，设备容器用 `shadow-xl`；浮层、弹窗和固定操作区按层级使用统一阴影 token。每张卡片都挂重阴影是低级视觉噪音，禁止。
- 一张卡片只承载一组相关信息或一个明确操作。
- 数字、热量、克数、日期和计时使用 `tabular-nums`，避免数值变化时跳动。
- 长文本要换行或截断，绝不能撑破横向布局。
- 图片必须设置固定比例或明确高度，加载前保留相同空间，避免布局跳动。
- 移动端文本列表保持单列；媒体卡片可使用 `repeat(3, minmax(0, 1fr))` 与 8px gap。宽容器才允许 `repeat(auto-fill, minmax(104px, 1fr))`。

## 9. 表单、弹窗、固定操作与状态

### 表单与提交反馈

- 每个输入控件必须有可见 `label`，并通过 `htmlFor` 与 `id` 关联；placeholder 只能提供示例，不能代替标签。
- 克数、身高、体重等数值字段使用匹配的 `type`、`inputMode` 和单位提示，让移动端弹出正确键盘。
- 同一提交区域只保留一个主按钮。提交后立即进入加载态并防止重复提交，随后明确展示成功或可恢复错误。
- 校验错误放在对应字段附近，说明如何修正；页面级错误只处理跨字段或服务端问题。
- 禁用按钮不能成为唯一错误提示。若用户尚未满足提交条件，页面必须说明缺少什么。
- 图片上传必须在加载前预留比例，上传、解析、失败和重试各有明确状态，不使用整页阻塞式加载。

### 弹窗与固定操作栏

- 常规弹窗最大宽 360px，紧凑弹窗最大约 310px，左右至少留 16px。
- 关闭操作命中区至少 44×44px。
- 底部操作区包含安全区 padding；主操作按钮撑满可用宽度。
- 破坏性操作必须经确认弹窗，不允许无提示直接执行。

### 加载、空态、错误与无权限

- 导航和页面框架持续可用；只替换依赖数据的局部内容，不使用全屏空白加载页。
- Skeleton 的尺寸、圆角、栅格列数和 gap 必须匹配最终内容。
- 空态、错误态、无权限态只出现在内容区，不覆盖顶部栏或底部导航。
- 错误不得只用红色表达，必须有文字和可恢复动作。
- 动效必须遵守 `prefers-reduced-motion`；减少动态时关闭或显著弱化非必要动画。

## 10. 图标、动效与交互反馈

- 图标默认 20–22px，线宽保持一致；只有品牌标识可使用独立图形语言。
- 图标按钮必须使用语义化 `button`，导航必须使用 `nav` 和真实链接；禁止用带 `onClick` 的 `div` 模拟交互元素。
- 常规颜色、透明度和位移动效控制在 150–200ms；复杂状态切换不超过 300ms。
- 不使用大幅缩放、连续漂浮、滚动劫持或强制 scroll-snap。桌面 hover 只能补充反馈，不能承载移动端无法触发的功能。
- 所有可点击元素在桌面设备容器中显示正确鼠标指针，并具备清晰的按下、焦点、禁用和加载反馈。
- 性能优化以测量为依据；图片和非首屏重内容可懒加载，但首屏主要操作不可因过度拆包延迟出现。

## 11. 视觉 token 与主题预留

采用设计稿 `src/tailwind-theme.css` 的浅色主题。只在统一样式层定义原始色值；业务组件引用语义 token，不散落色值、私有阴影或私有圆角。

| Token | 设计稿值 | 用途 |
|---|---|---|
| `background` | `hsl(140 20% 97%)` | 浅绿灰页面底 |
| `foreground` / `card-foreground` | `hsl(150 35% 12%)` | 深绿黑正文 |
| `card` / `popover` | `hsl(0 0% 100%)` | 白色内容卡与浮层 |
| `primary` / `ring` | `hsl(152 40% 30%)` | 深森林绿 CTA、选中导航、焦点 |
| `primary-foreground` | `hsl(0 0% 100%)` | 主按钮文字 |
| `secondary` / `muted` | `hsl(145 25% 94%)` | 桌面外底、摘要格与提示底 |
| `muted-foreground` | `hsl(150 15% 45%)` | 辅助文字；小字必须验证对比度 |
| `accent` | `hsl(148 32% 90%)` | 浅绿交互背景 |
| `accent-foreground` | `hsl(152 40% 25%)` | 浅绿底上的强调文字 |
| `border` / `input` | `hsl(145 20% 88%)` | 卡片、输入及分隔线 |
| `destructive` | `hsl(0 65% 50%)` | 删除与错误 |
| `success` | `hsl(152 45% 38%)` | 成功反馈 |
| `warning` | `hsl(22 80% 55%)` | 待补充与提醒 |
| `info` | `hsl(205 70% 50%)` | 信息提示 |

营养素颜色依据实际 `MacroRingChart`，分别定义 `macro-protein: #2D6A4F`、`macro-fat: #5A7A68`、`macro-carbs: #E76F51`，对应蛋白质、脂肪、碳水；不用早期说明的蓝/黄/紫配色。环图配文字图例与克数，报告中直径 180px（组件默认 160px），内外半径约为直径的 32% / 45%。设计稿按克数绘制扇区，不得误标成能量占比；环中心热量与报告应使用同一后端权威结果，不复制前端独立计算。没有有效数据时显示空态。

基础圆角 token 为 8px，派生小块 6px、卡片 12px，桌面框架 32px。轻阴影采用绿色低透明度：设计稿 `shadow-sm` 为 `0 2px 8px hsl(152 35% 20% / 0.06), 0 1px 2px -1px hsl(152 35% 20% / 0.04)`；统一配置后引用。

后续在 [`frontend/src/styles.css`](../../frontend/src/styles.css) 映射上述 token；本次只更新文档，不改样式。设计色值是还原基准，不代表对比度已经验收：辅助小字、警告底与焦点等组合若不达标，应统一调整对应 token 深浅后复验。

深色模式仅预留，不实现开关：

- 新组件不得直接使用 `white`、`black`、具体灰阶或“仅浅色”色值表达 UI 语义。
- 通过语义 token 表达背景、文字、边框、状态和焦点；将来可在 `.dark` 下替换 token，不改业务组件。
- 未实现主题切换前，不在 UI 中出现“深色模式”开关、设置项或无法生效的图标。

## 12. 可访问性与验收底线

- 所有图标按钮有明确 `aria-label`；不能只靠图标猜动作。
- 正文与背景对比度至少达到 WCAG AA 4.5:1；大号文字至少 3:1；焦点环必须可见。
- 状态必须包含默认、按下、禁用、焦点和加载中；状态不只用颜色表达。
- 关键操作最小 44×44px；320px 宽和 200% 缩放下不得产生横向滚动。
- 页面只能有一个主要纵向滚动容器；弹窗和横向列表的滚动与内容区独立，但禁止难以判断目标的嵌套纵向滚动。
- 每页只保留一个 `main` 地标，由布局层提供；页面组件使用 `section` 或普通容器，不能照搬设计稿中布局与页面嵌套 `main` 的结构。
- 移动端可弱化滚动条；桌面设备容器不强制隐藏滚动提示，确保用户知道内容仍可滚动。
- AppShell 提供“跳到主要内容”的键盘跳转入口；键盘 Tab 顺序必须与视觉顺序一致，弹窗不得形成键盘陷阱。
- 新增或重做用户可见页面后，必须执行组件测试，并按 [前端规范](../../frontend/AGENTS.md) 使用 Codex 内置浏览器走真实页面与公开 API 验收。

### 响应式验收矩阵

| 场景 | 必验宽度/环境 | 验收重点 |
|---|---|---|
| 极小手机 | 320px | 无横向滚动，主要操作和表单可用 |
| 常见手机 | 375px | 内容层级、输入键盘、固定操作栏 |
| 设计基准 | 430px | 间距、卡片、四 Tab 和安全区 |
| 桌面容器 | 768px、1024px、1440px | 设备容器居中、阴影边框、内容仍按 H5 呈现 |
| 可访问性 | 200% 缩放、键盘、减少动态 | 焦点、阅读顺序、无内容遮挡 |

每次页面验收至少覆盖加载、空态、错误、成功和长内容五种状态；只看理想数据截图不算完成。
