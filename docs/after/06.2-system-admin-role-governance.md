# Phase 06.2：系统管理与角色治理

## 这一阶段解决什么问题

后台原先只有 `user` 与 `admin` 两种角色，也会在每次后台请求中读取数据库校验管理员身份，但缺少公开的账号治理入口。这个阶段补齐一级“系统管理”导航，并在其下提供“管理员管理”和“角色管理”。

角色仍然是固定枚举，不做自定义角色编辑。这样能避免前端出现一套看似可配置、后端却没有完整权限模型支撑的假 RBAC。

## 请求链路

管理员管理页面通过后台公开 API 查询账号：

1. React 页面提交邮箱、角色、状态和分页条件。
2. FastAPI 先验证 access token，再用数据库中的实时角色执行管理员校验。
3. Service 校验查询参数或角色变更命令。
4. Repository 使用 SQLAlchemy 查询 PostgreSQL，并返回账号总数或角色统计。
5. Schema 将 ORM 模型投影成受控响应，前端再用 Zod 做一次运行时校验。

角色变更使用 `PATCH /api/v1/admin/users/{user_id}/role`。命令必须带非空原因和 `Idempotency-Key`，并禁止修改自己、提升未激活或未验证账号、以及把系统降到没有可用管理员的状态。

## 为什么降权后保留普通用户登录态

access token 只证明用户身份；后台每次请求仍从数据库读取当前角色。把管理员降为普通用户后，不删除其认证会话，因此用户端功能继续可用，但下一次后台 API 调用会立即得到 403。

这个边界比“前端隐藏菜单”可靠：即使旧页面还停留在浏览器里，也无法继续读取或修改后台数据。

## 事务、并发与幂等

升降权与审计写入在同一个数据库事务中完成：

- 锁定操作者和目标账号，避免并发修改覆盖。
- 使用事务级 advisory lock 串行化管理员角色治理。
- 写入角色审计记录和通用后台审计事件。
- 相同操作者重复提交同一个幂等键时，返回首次结果而不是重复变更。
- 任一步失败都会回滚角色和审计，避免“权限变了但无记录”的半完成状态。

## 测试怎么覆盖

- Service 单测使用 fake repository，覆盖查询、升降权、身份限制和幂等。
- API 单测覆盖认证、参数映射和错误状态码。
- PostgreSQL 集成测试验证真实事务、审计落库，以及降权后普通用户会话仍可刷新但后台接口返回 403。
- 管理后台组件测试覆盖表格、筛选和确认原因。
- Playwright 通过公开注册、邮箱验证、后台登录和公开 API 完成提升、访问角色页、降权与 403 的完整用户路径。

## 常见错误

1. 只根据前端缓存的角色控制按钮：这不能形成权限边界，后端必须实时查库。
2. 角色变更不要求原因：之后只能知道“谁改了”，无法解释“为什么改”。
3. 先改角色再单独写审计：第二步失败会制造不可追溯变更，必须共用事务。
4. 降权时无差别撤销全部会话：这会把后台权限治理错误扩大成普通用户账号封禁。
5. 开放自定义角色但仍在代码里写死权限：这是两套相互矛盾的权限模型，本阶段明确不做。
