# 06.3 向量检索管理：构建不等于激活

## 为什么要单独管理

向量构建会把当前合格目录的受控名称交给 embedding Provider，因而有费用和版本风险。后台页面不能把“创建任务”“任务完成”和“切换线上检索”混成一个按钮：前两步只是生成可检查的候选版本，最后一步才会影响用户分析。

## 请求链路

```text
管理后台页面
  → features/vector-retrieval/api/（Zod 校验、内存 access token、幂等键）
  → /api/v1/admin/vector-space-builds*
  → AdminService（数据库 RBAC、审计、冻结 manifest）
  → AdminRepository（PostgreSQL 任务/完成证据/active pointer）
```

页面只接收构建 ID、模型身份、任务计数、状态与 `activation_ready`。它不会接收菜名清单、embedding 数组、Provider 原文或 API Key。

## 三个动作

1. **回填检索名称**：为升级前已发布的合格目录补齐派生检索名称；若已有激活空间，可能同时排队 Embedding 任务。原因和幂等键写入审计。
2. **创建构建**：固定模型、维度、adapter 与 retrieval 版本，冻结当前 `eligible` 名称 ID 清单并排队。没有合格检索名称时后端拒绝创建，不会产生 `0/0` 的伪完成构建。
3. **重试失败项**：仅重置该冻结构建内、尚未用完尝试次数的失败 job；原因和幂等键写入审计。
4. **激活**：后端重新校验非空 build manifest、完成证据、每项 ready embedding，以及冻结的评测发布身份。页面只在服务端返回 `activation_ready: true` 时显示按钮。

当前 DashScope `text-embedding-v4` 可以创建和观察构建，但它没有对应的冻结评测发布身份时，`activation_ready` 会保持 false。这是正确的 fail-closed 行为，不能为了验证而绕过。

## 测试方法

```bash
cd admin-frontend && npm test -- --run src/features/vector-retrieval/VectorRetrievalPage.test.tsx
cd admin-frontend && npm run typecheck
cd backend && uv run pytest tests/unit/test_admin_catalog_api.py -q
```

前端测试确认固定 DashScope 命令、失败重试、403 安全空态和不显示未准入的激活按钮。后端测试确认控制面返回的是安全投影，并要求幂等键。

## 常见错误

- **看到“已完成”就激活**：错误。完成只说明任务完成，不说明评测证据与冻结身份有效。
- **把 API Key 显示在配置页**：错误。页面只显示可审计的模型身份。
- **用前端按钮禁用代替权限**：错误。每个 API 仍在服务端重新读取管理员角色。
