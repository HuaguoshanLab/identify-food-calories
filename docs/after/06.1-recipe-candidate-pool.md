# 菜谱候选池与按需餐单生成

## 为什么“营养目录”不等于“菜谱管理”

营养目录回答的是“某个可计算食物每 100 克有什么营养”；它是数值权威。菜谱候选回答的是“这道已准备好的菜可以在哪一餐出现、一次吃多少、做法和口味是什么”；它是运营配置。把两者混成一张表会让份量、餐次或做法修改时错误地污染营养真相。

一个候选只保存目录引用、显示名、单份克数、标签和生命周期，不复制任何能量或三大营养素。计算时，规划服务仍以 `food_id + catalog_version + grams` 调用 nutrition 的确定性计算器。

目录引用可来自两类已合格数据：系统导入的 `food_catalog_items`，或管理员已审核、发布且当前仍合格的 `catalog_publications`。后者不是 `food_catalog_items` 的副本；`0024` 迁移要求候选二选一引用，以免后台已发布目录无法导入菜谱。

## 管理员导入链路

请求路径如下：

```text
CSV → import-preview（仅语法/行校验）
    → import（管理员 RBAC、名称唯一且当前合格校验）
    → managed_recipe_candidates + append-only admin_audit_events
    → enable / disable / delete（软删除）
    → 下一次规划查询候选池
```

CSV 列为“关联目录菜品名称、餐次、单份克数、份量说明、做法标签、口味标签、状态”。预览不写库；确认导入必须有原因和 `Idempotency-Key`。同一个键重试同一个命令会回放结果，复用到不同内容会冲突。名称不存在、重名、失格或已停用的目录项一律拒绝，系统不会猜测关联或自动创建营养数据。

“删除”只设置候选的 `deleted_at`，不会删除营养目录，也不会改写已保存计划。启用、停用、删除都要求原因，并为每行和批次写审计事件。

## 从候选到用户计划

规划查询只返回状态为 enabled、未软删除且目录仍可计算的候选。三餐早餐、午餐、晚餐必须齐全；加餐只是候选池中有适用项时才可返回。历史计划没有加餐不会被补造一张卡。

用户的最近三份已归档计划中的候选 ID 会作为轮换历史。每个餐次优先从未近期出现的候选中随机选择；若候选池过小、全部近期出现，才回退到完整可用池。这个随机步骤只影响“选哪一道菜”，营养计算、目标区间校验、目录资格和历史快照全部保持确定性和可追溯。

计划存档会记录候选 ID、候选 revision、目录版本和审计版本。此后即使候选被停用、软删除或目录失格，旧计划仍读自己的不可变快照；只有新生成计划会排除它。

## 测试方式

- 领域单测：验证候选没有营养副本、三餐必需而加餐可选，以及最近计划优先去重。
- PostgreSQL 集成测试：验证 enabled/失格/停用/软删除过滤，并验证管理员已发布目录可作为候选引用；补充无对应菜谱、餐次不匹配、目录版本失效、发布撤销、忌口及当前菜谱排除。
- 后台浏览器 E2E：注册并提升测试管理员，真实页面新建、审核、发布目录，导入三条候选，再批量启用、停用、删除。
- 内置浏览器：未登录访问 `/admin/recipes` 被服务端会话 guard 重定向到后台登录；管理员端完整操作另由上述真实 E2E 覆盖。

运行关键检查：

```bash
cd backend
uv run python tests/run_pg.py --env-file .env.test.example -- \
  uv run --extra dev pytest tests/planning/test_planning_service.py tests/integration/test_managed_recipe_candidate_repository.py -q

cd ../admin-frontend
E2E_ADMIN_BACKEND_PORT=8003 E2E_ADMIN_USER_FRONTEND_PORT=5183 E2E_ADMIN_FRONTEND_PORT=5184 \
  npm run test:e2e -- tests/e2e/recipe-management.spec.ts
```

PostgreSQL 测试必须经过 `backend/tests/run_pg.py` 的隔离库合同；不得把测试连接到开发库。

### 候选展示与确认之间的资格变化

调整链路先将营养检索结果的 `food_id + catalog_version` 交给 `PlanningService.keep_replaceable_food_identities`。服务通过真实 Repository 读取已启用且关联合格目录的菜谱，再检查餐次、当前菜谱排除、忌口和营养可计算性。目录命中但没有菜谱时，仍不能成为替换候选。

用户确认后，`compose_daily_meals` 重新读取目录和菜谱资格，并按实际份量计算营养。同一菜品关联两个菜谱时，菜品候选仍只有一项；排除一个菜谱后，可使用另一个合格菜谱。当前已接入具体菜谱选择：只有一个合格菜谱时直接替换；多个时进入 `recipe_clarification`，展示餐次、份量、做法和口味，不默认选中。用户只提交菜谱 ID 和 revision；后端重新读取资格及版本，发生停用或修改时重新提供候选，不能退回其他菜谱静默替换。候选最多展示 20 条。

`test_admin_disable_between_candidate_offer_and_confirmation_is_reread` 使用两个独立 PostgreSQL 连接：读连接先得到候选并证明可组合；管理连接提交禁用；读连接随后复核，必须得到空候选和 `REPLAN`，不得返回替换餐单。测试完成后按本次 fixture ID 清理已提交数据。它验证的是“展示后、确认前禁用”的交错事务，不证明确认已读完之后与最终存档之间的竞争已被锁定，也不替代公开 API 或浏览器验收。

## 常见错误

1. **把菜谱名称当作营养数据。** 名称只是关联键和显示文本；热量必须每次从当前目录按克数重算。
2. **只检查 CSV 格式，不检查目录资格。** 格式正确但目录不存在、歧义、失格或停用都不能导入。
3. **停用候选时修改历史计划。** 历史是快照，生命周期只影响未来查询。
4. **把加餐固定为第四餐。** 加餐是按需返回；没有合格候选时只能显示三餐。
5. **用前端隐藏代替 RBAC。** 导入、导出和批量操作的授权必须由后端数据库当前角色确认。
