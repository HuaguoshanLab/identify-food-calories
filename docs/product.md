# 产品说明

## 定位与用户

本项目帮助用户通过文字或餐食图片获得可追问、可校验、可追溯的饮食分析，并结合身体资料、目标和明确偏好生成可调整的一日餐单。所有建议属于普通饮食参考，不提供医疗诊断、治疗或处方级建议。

- 普通用户：分析一餐、确认份量、保存实际饮食并查看摄入记录。
- 有体重管理目标的用户：设置个人资料与目标，生成和调整餐单，管理长期偏好。
- 管理员：维护营养目录与菜谱，管理检索索引、权限、运行配置和审计。
- 学习者：从功能教程追踪请求、模型理解、工具计算、状态恢复和业务存储。

项目入口和运行命令见[根 README](../README.md)，开发约束见[AGENTS.md](../AGENTS.md)，后续工作见[待办](backlog.md)。本文描述产品合同与当前实现边界；验收条件不是测试通过声明。

## 当前实现边界

1. **模型负责理解，工具负责计算。** DeepSeek 文本 Provider 与 Qwen 视觉 Provider 输出受校验的结构化信息；营养、身体目标和餐单校验来自确定性规则。Fake Provider 验证流程，不代表真实模型效果。
2. **编排是原生 StateGraph。** [Agent 图实现](../backend/app/agent/graph.py)把餐食分析和饮食规划拆成独立节点与条件边；应用服务通过 LangGraph PostgreSQL Checkpointer 恢复状态，等待态使用 `interrupt()`，恢复使用 `Command(resume=...)`。周总结使用非持久化 `StateGraph`。
3. **餐单来自受控候选和规则。** 生成与调整经工具进入规划领域服务，不是模型自由编造食谱与营养值。有限候选可能无法满足所有目标，必须保留失败和缺口解释。
4. **存储各有职责。** PostgreSQL 保存权威业务数据；Checkpoint 保存短期运行状态；长期偏好由本地账本控制，Mem0 保存受控副本，不能覆盖业务事实。
5. **三个应用保持独立。** 用户端与管理端分别构建，共用 FastAPI 模块化单体。后台菜单和页面守卫不能替代后端权限校验。

## 范围与安全边界

- 不提供医疗诊断、治疗方案或过敏安全保证；已知忌口匹配不等于完整配料与过敏原覆盖。
- 不让模型自由决定最终营养值，不以置信度字段冒充识别准确率。
- 图片仅用于分析，执行元数据剥离与删除策略；密钥、原图、完整模型思维链和不必要的敏感信息不进入日志。
- 模型经 Provider 接口调用，参数和输出运行时校验，调用需具备超时、失败分类及费用边界。
- 不训练自有视觉基础模型；图像生成模型不承担食物识别。
- 保持模块化单体，当前不引入微服务、Kafka、Kubernetes 或自由互相调用的多 Agent 网络。
