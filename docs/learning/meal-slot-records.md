# 餐次与补录时间：从表单到权威记录

## 为什么餐次不能由模型或保存时刻决定
早餐可以在晚上补录，夜班用户也可能在傍晚吃早餐。餐次是用户确认的业务事实；模型识别和营养计算不参与归类。`meal-slot.v1` 包含早餐、午餐、晚餐、加餐。页面仅初始预选：05:00–10:59 早餐、11:00–14:59 午餐、17:00–21:59 晚餐，其余加餐。这是可修改的交互建议，不是营养规则；修改时间不会覆盖已选餐次。

## 请求链路与数据流
分析页使用 records 公开 API 导出的表单合同，React Hook Form + Zod 校验日期有效且不在未来；浏览器把本地时间转为带时区 UTC 时间，并发送设备 IANA 时区与 `meal_slot`。FastAPI 的 Pydantic 枚举拒绝非法餐次，Service 再校验领域值与时间，通过带 `user_id` 的 Repository 写入 PostgreSQL。营养值继续只来自已完成分析的确定性报告。

`POST /api/v1/meal-records` 接受 `thread_id`、`command_key`、`consumed_at`、`time_zone`、`meal_slot`。相同分析重复保存仍复用已有记录，不通过重试覆盖元数据。前端提交期间锁定操作，失败保留输入。

`PATCH /api/v1/meal-records/{id}` 使用同样的时间/时区/餐次事实。省略 `meal_slot` 保留原值，显式 null 清除分类；选择餐次则更新。时间变更同步更新本地日期，餐次变更不重算营养快照。成功后使 dashboard 缓存失效，详情和历史读取服务器结果。

## 迁移与历史兼容
Alembic `0020` 在 `0019` 后增加可空 `meal_slot` 和四值 CHECK 约束。历史行保留 null，前端显示“未分类”，用户可在编辑页补选。旧客户端省略餐次仍可保存，避免升级期间破坏调用方；新分析页始终提交明确餐次。不能根据 `created_at` 或 `consumed_at` 批量猜测旧餐次。

## 测试方法
- Service fake repository：四种餐次、null、非法值、时间单独修改、显式清除、幂等保存和营养快照保持。
- API：非法枚举返回 422；未知/他人记录保持统一 404。
- PostgreSQL：迁移链、实际保存/编辑/读取、旧记录 null 与租户隔离。
- 组件：补录、未来时间拦截、连续点击只提交一次、失败保留输入、旧记录补分类。
- E2E：上海和洛杉矶两种时区完成分析、早餐保存、历史显示、晚间补录仍保持早餐，再修改为加餐；320px 编辑布局。
- 内置浏览器：从实际分析页生成报告，阻止未来时间，保存过去早餐，再编辑时间和餐次，观察营养值保持。

## 常见错误
- PATCH 漏传 `time_zone`：即使 UI 看起来正常，后端也会拒绝。这次修复了已有编辑请求的遗漏。
- 修改时间就覆盖餐次：破坏用户已确认的事实。
- 直接填充历史餐次：把猜测包装成权威数据。
- 只改 records DTO：历史页用 dashboard 独立投影，还必须同步 schema 和映射。
- 把表单放到其他 feature 的私有组件：分析页只能通过登记的 records API 边界复用合同。
