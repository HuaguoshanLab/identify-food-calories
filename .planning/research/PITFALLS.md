# Pitfalls Research

**Domain:** 移动端单图中式外卖多菜识别、估重与热量估算
**Researched:** 2026-08-26
**Confidence:** HIGH（识别/估重、图片安全、隐私和评测方法有权威或同行评审来源；中国食物成分数据商业授权状态为 LOW，必须单独核实）

## Executive Risk View

这个产品最危险的失败不是偶尔认错菜，而是把三个不可观测量——**真实尺度、隐藏配方、实际用油糖**——包装成精确克数和精确千卡。单图可以支持“快速粗估 + 用户修正”，不能支持称重级或医疗级结论。系统性综述显示，食品图像能量估算研究的误差和验证方法差异很大，且简单单一食物通常优于多食物场景；食物量化工具的研究甚至出现从大幅低估到数倍高估的结果。路线图因此必须先建立真实外卖评测集、受控菜品目录和误差模型，再优化界面或扩品类。

第二类致命失败是**评测自欺**：用同一标准菜谱既生成“真实热量”又驱动预测，用随机图片切分让同一商家/同一订单近重复图跨集合，反复查看测试集调 prompt，或只报总体 Top-1、克数中位误差和区间覆盖率。这样的指标可以全部达标，真实用户仍然得到错误且过窄的区间。测试必须按订单/商家/拍摄批次分组，保留一次性封存测试集，并同时考核识别召回、尾部误差、分层覆盖率和区间宽度。

第三类失败来自“免登录 + 图片上传 + 按次付费模型”的组合：恶意文件、图片解码炸弹、图中提示注入、匿名刷量、重试风暴和境外模型处理，会同时击穿安全、成本、延迟和隐私。图片必须在进入模型前经过像素级限制、安全解码重编码、元数据剥离；模型只输出受限候选，不能获得工具或数据库写权限；请求必须有频率、并发、超时、重试和日预算上限。

## Critical Pitfalls

### Pitfall 1: 把“菜名分类”误当成“多菜完整识别”

**What goes wrong:**
模型能给出一个看似正确的主菜名，但漏掉米饭、小菜、酱汁或重复算同一格食物；总体 Top-1 仍然很好，整餐热量却系统性偏低或偏高。混菜、遮挡、相似菜（宫保鸡丁/辣子鸡、鱼香肉丝/京酱肉丝）还会让具体菜名变成无证据的猜测。

**Why it happens:**
公开食品分类基准多以单菜或清晰餐盘为主，分类准确率不衡量“图中有几项、是否全部找全”。同行评审综述也指出，多食物图像通常比单一/简单食物误差更大。将模型自由文本直接映射成菜名，还会掩盖目标菜目录之外（OOD）的输入。

**How to avoid:**
- 先定义实例级标注：每个餐盒格/独立食物区域一个实例，允许“不可判定”“目标目录外”“非食物”。
- 评测同时报告实例级 precision/recall/F1、每餐漏项率、重复项率、Top-1/Top-3；不能只报图片级 Top-1。
- 只允许输出受控目录 ID；低置信度必须给 2–3 个目录内候选，明显 OOD 时拒识并提示手动选择。
- 对米饭、主菜、配菜、汤/饮料分别分层统计；整餐总热量指标不能掩盖漏项。

**Warning signs:**
- 演示图“主菜都认对了”，但预测项数经常少于人工标注项数。
- Top-1 很高，整餐热量仍持续低估；错误主要来自漏掉米饭、酱汁、小菜。
- 模型会输出目录之外的具体菜名，或每张图都强行给出答案。

**Phase to address:**
**评测集与识别契约阶段（模型选型前）**。未建立实例级基准和拒识规则，不应开始以 Top-1 选模型。

### Pitfall 2: 从单张二维图像伪造确定的克数

**What goes wrong:**
同样的像素面积可能对应不同餐盒尺寸、拍摄距离、视角、堆叠高度和食物密度。系统输出“237 g”一类精确数字，让用户误以为有称重依据；误差进一步乘以每 100 g 热量，污染单项和整餐结果。

**Why it happens:**
单目图像存在尺度歧义，遮挡部分和厚度不可见。单图食物体积研究经常需要已知尺寸参照物、已知餐具模型或受控拍摄条件；真实外卖图通常没有可靠参照。所谓“标准餐盒”也不是统一规格，筷子、手机等物体可能不在同一平面。

**How to avoid:**
- 把模型克数视为先验估计，不是测量值；显示可编辑的合理整数和区间，避免个位数精度。
- 建立菜品 × 容器类型 × 商家/规格的真实称重分布；没有可验证尺度时，以分布先验为主，视觉只做有限修正。
- 只有检测到已验证尺寸的容器型号且透视条件合格时，才使用尺度校正；不要假定所有餐盒、筷子尺寸相同。
- 按“有可靠参照/无参照、俯拍/斜拍、遮挡程度、容器类型”分别评测；除了中位相对误差，还报 P90、系统性偏差和极端小份/大份误差。
- 对模糊、过暗、严重遮挡、只拍到局部的图片拒绝估重并给具体重拍指引。

**Warning signs:**
- 克数输出大量非整十数，但没有尺度来源或容器识别证据。
- 同一份餐从不同角度拍摄，克数波动超过 25%。
- 中位误差达标，但 P90 很差；小配菜的相对误差无限放大或大份餐持续低估。
- 团队讨论“让 prompt 更会估重”，却没有新增称重数据。

**Phase to address:**
**真实数据采集与估重校准阶段**。在结果页定稿前必须证明 QLT-03 在真实外卖分层上成立。

### Pitfall 3: 忽略隐藏油、糖、酱汁和同名菜配方差异

**What goes wrong:**
菜名和可见份量都判断正确，热量仍严重错误。炒、炸、勾芡类中餐的油糖可能已经吸收或藏在酱汁里；同名菜在商家间的肉菜比例、裹粉、用油和收汁程度差异很大，照片无法可靠恢复。

**Why it happens:**
视觉模型擅长可见外观，不具备配方记录。国家卫健委的餐饮营养标识指南要求能量计算依据**原料、烹调油及调味品用量**，并要求过程完整、真实、可溯源；仅凭成品照片缺少这些关键输入。近期食品图像综述也明确指出，烹饪方式、配料和用油无法只从一张照片准确取得。

**How to avoid:**
- 每道菜保存单位重量热量的经验分布，而不是单个常数；分布应来自多商家、不同价位和做法的称重/配方样本。
- 将不可见配方误差与份量误差分开建模，再传播到总热量区间；不要用统一“±20%”。
- 对高油糖不确定菜品设置更宽区间和显著说明；允许用户选择“少油/常规/重油”“酱汁是否吃完”等少量高价值修正项，但不要增加主流程操作负担。
- 参考热量必须由受控目录计算；视觉模型不得自由生成每 100 g 热量或隐藏油克数。
- 验收区间覆盖率时按菜系/烹饪法/商家分层，并同时限制平均区间宽度，防止用极宽区间作弊。

**Warning signs:**
- 所有菜都使用相同百分比区间，或区间宽度只随克数线性变化。
- 清炒、油炸、勾芡菜的误差与蒸煮菜相同。
- 实测中“菜名正确”的样本仍有明显热量偏差，且偏差随商家聚集。
- 产品文案只说“AI 识别误差”，没有明确油糖和配方不可见。

**Phase to address:**
**菜品目录与热量区间建模阶段**。这是 MVP 数据地基，不可推迟到上线后。

### Pitfall 4: 营养数据“可访问”不等于“可商用、可直接套用”

**What goes wrong:**
团队抓取《中国食物成分表》、网站数据或竞品菜单后直接商用，后期才发现版权、数据库权利、署名、再分发或 API 条款不允许；或者用 USDA 的基础食材/美国配方直接代表中式成菜，形成合法但语义错误的数据。

**Why it happens:**
国家卫健委指南推荐参考《中国食物成分表》等权威数据库，但“被官方推荐参考”并不自动授予复制、再分发或商业产品使用权。本次检索未找到《中国食物成分表》明确、可验证的开放商业许可。相反，USDA FoodData Central 官方明确为 CC0 公共领域，但其数据覆盖和中式外卖配方匹配度有限。

**How to avoid:**
- 在导入任何数据前建立来源台账：权利人、版本、字段、许可文本、商用/修改/再分发权限、署名要求、取得日期、更新策略。
- 将《中国食物成分表》商业使用列为**上线阻断项**：取得权利人书面许可或律师确认前，不批量复制发布其数据。
- USDA 只补充基础食材和可匹配项目；中式成菜应使用自建标准配方/合法授权数据，并记录每个数值的可追溯计算链。
- 评测图片、商家菜单、用户图片也分别记录授权用途；“可公开浏览”不等于可用于训练或永久存档。
- 数据版本化，旧结果保留 `source_id`、版本和计算规则，避免静默更新后无法复现。

**Warning signs:**
- 数据表只有“来源：中国食物成分表”，没有版次、页码/条目、许可证明或字段级 lineage。
- 团队把“非商业研究数据集”放进产品评测或训练；FoodNExTDB 等公开仓库就明确限制商业用途。
- 相同菜名在多个来源间热量差异很大，却直接取平均且不记录原因。
- API key 暴露在前端，或线上请求依赖第三方公共 API 的默认速率限制。

**Phase to address:**
**数据授权与目录地基阶段（任何模型集成前）**。授权未闭环时可做隔离研究原型，不得作为可上线数据链。

### Pitfall 5: 把结构化输出和模型自报置信度当成真实性保证

**What goes wrong:**
JSON 能解析，但菜品 ID 不存在、克数为负、同一食物重复、候选概率不守恒、总热量和明细不一致；或者模型用“0.93”表达强烈自信，实际在相似菜或目标目录外样本上严重过度自信。重试可能得到另一个同样合法但语义不同的答案。

**Why it happens:**
JSON Schema 只约束形状，不证明字段语义正确。模型输出本质上有随机性，模型快照和提示变化也会改变行为；VLM 的 verbalized confidence 已有研究发现校准较差。让同一个模型同时识别、估重、生成营养值、解释和自评置信度，错误会相互强化。

**How to avoid:**
- 使用严格 schema 后仍执行确定性验证：目录 ID 白名单、项数上限、克数范围、去重、候选集合、数值有限性和总和重算。
- 营养计算只在代码中由 `dish_id × grams × catalog_value` 完成；忽略模型返回的 kcal。
- 置信阈值来自独立校准集上的经验准确率，而非直接展示模型自报概率；按菜品和困难场景检查 reliability diagram/ECE、选择性准确率和拒识率。
- 固定模型快照、prompt、schema 和预处理版本；每次变更跑回归集和封存集。解析/语义失败只允许一次有界修复，之后友好失败，禁止无限重试。
- 输出中保留模型版本、prompt 版本、目录版本、验证失败码和供应商 request ID，但日志不保存原图或完整敏感 payload。

**Warning signs:**
- 团队说“用了 Structured Outputs，所以不会 hallucinate”。
- 置信度集中在 0.8–1.0，低置信候选几乎从不出现。
- 同一图片重复请求时菜名/克数显著波动；升级模型别名后指标无告警变化。
- 后端接受模型给出的热量，或只检查 JSON parse 成功。

**Phase to address:**
**推理契约与模型校准阶段**，并在**上线可靠性阶段**加入版本回归门禁。

### Pitfall 6: 用错误的指标和泄漏测试集制造“达标”

**What goes wrong:**
QLT-01～04 表面达标，真实流量却失效。典型做法包括：同一订单的多角度图或近重复图片跨 train/test；同一商家菜品同时出现在两侧；用测试集反复调 prompt；使用模型可能见过的公开网图；用标准菜谱计算值同时作为预测来源和“真值”；只报中位相对误差；用无限宽区间轻松达到 80% 覆盖。

**Why it happens:**
随机图片切分最省事，但食物图像高度重复。Google 的 ML 指南明确指出测试集会因反复使用而“磨损”，且训练、验证、测试之间不能有重复。食物图像系统综述也发现研究间 ground truth 和数据集差异巨大，导致结果难以直接比较。

**How to avoid:**
- 数据采集时就生成 `order_id / restaurant_id / shoot_session_id / source_hash`；按组切分而不是按图片随机切分，使用感知哈希去除近重复。
- 三层数据：开发集（可调）、冻结验证集（选模型/阈值）、封存测试集（里程碑只跑一次）；上线前再收一批时间后移、商家未见的 shadow set。
- 菜名真值由人工双标/仲裁；克数来自实际称重；参考热量优先来自配方原料、用油调味品称重和可追溯计算。不能让被测系统使用的目录值自己证明自己正确。
- 指标必须成套：实例召回/精确率、Top-1/Top-3、克数 MdAPE + P90 + signed bias、总 kcal MAE/MAPE、80% 区间的总体及分层覆盖、平均宽度/归一化宽度、拒识率和失败率。
- 对每道菜、烹饪法、商家、容器、光照、角度、遮挡、目标目录外输入报告置信区间；总体均值不能替代最差分层。

**Warning signs:**
- 没有订单/商家分组字段，只有 `image_id`。
- 每次 prompt 修改后都查看“最终测试集”分数。
- 区间覆盖提高时区间宽度同步失控，或 80% 总覆盖下某些高油菜仅 40%。
- 真实热量标签恰好等于目录中心值 × 实际克数，隐藏油糖误差为零。

**Phase to address:**
**评测设计阶段必须先于模型选型**；封存集在**上线验收阶段**执行，之后持续采集漂移集。

### Pitfall 7: 图片处理链既泄露隐私，又成为攻击入口

**What goes wrong:**
照片可能带 EXIF 定位/设备信息，背景可能出现人脸、订单小票、姓名、电话、住址或支付信息；原图被对象存储、日志、CDN、备份和模型供应商分别保留，所谓“分析后删除”只删了一份。恶意上传还可利用 MIME 欺骗、畸形图片、超大像素/解码炸弹攻击处理库，或在图片中藏提示词操纵多模态模型输出。

**Why it happens:**
开发者只检查扩展名和压缩前字节大小，信任客户端 `Content-Type`，把原文件直接交给图像库和 VLM。OWASP 明确指出上传文件可利用解析器、伪造类型并耗尽资源；OWASP GenAI 也将文件中的间接提示注入和图像隐藏指令列为多模态风险。

**How to avoid:**
- 只接受业务必需格式；服务端检查 magic bytes、最大压缩字节、最大解码像素、长宽比和帧数，设置解码 CPU/内存/时间限制。
- 在隔离进程中用维护中的安全库解码并重编码为干净 JPEG/WebP，剥离 EXIF/ICC/XMP 和原文件名；模型只接收重编码副本。
- 原图默认不落盘；如异步处理必须暂存，使用随机对象键、私有桶、短 TTL、服务端加密、无公开 URL，并验证原图、派生图、队列 payload、日志、备份和供应商侧全部删除路径。
- VLM 无工具权限；图中文字一律视为不可信内容，后端只接受白名单目录 ID 和数值边界。建立带图片提示注入、二维码、屏幕截图和非食物图的对抗集。
- 对人脸/小票/敏感背景可在本地或入口侧检测并提示裁剪；不得把用户图片默认纳入训练/人工标注，二次用途须另行、明确授权。

**Warning signs:**
- 仅靠扩展名或 `Content-Type` 判断图片；只限制 10 MB，不限制解码后像素。
- 对象存储可以公开访问，日志中出现 base64 图片、签名 URL 或完整请求体。
- 删除测试后，缩略图、CDN、队列死信或供应商控制台仍能找到图片。
- 带“忽略系统指令”文字的图片能让模型输出目录外内容或超范围数值。

**Phase to address:**
**图片入口与安全隐私阶段（首次接入真实用户图片前）**，并在**上线前安全测试阶段**做恶意样本和删除链路演练。

### Pitfall 8: 免登录并不等于无需隐私合规

**What goes wrong:**
产品没有账号，却仍通过 IP、设备标识、日志、图片、EXIF、小票和膳食/健康语境处理可识别信息；境外 VLM 接收图片但隐私政策没有告知接收方、地域、保存期限或删除方式。若图片或推断与医疗健康信息关联，可能触发敏感个人信息的更严格要求。

**Why it happens:**
团队误把“匿名使用”理解成“匿名数据”。《个人信息保护法》要求目的明确、最小范围、最短必要保存期限；委托处理需约定目的、期限、方式和安全措施并监督受托人，向境外提供还涉及专门条件、告知和单独同意。是否构成敏感个人信息取决于具体处理语境，不能凭产品自称“非医疗”自动排除。

**How to avoid:**
- 做数据流图和 PIIA：浏览器 → 自家后端/对象存储 → 模型供应商 → 日志/监控/客服；逐项记录字段、目的、法定基础、地域、TTL、删除和分包商。
- 默认原图分析完成后立即删除；只留去标识化指标。确需留存失败样本时采用单独、可撤回的 opt-in，并明确用途和期限。
- 与模型/云供应商签委托处理条款，核实训练使用、人工审阅、滥用监控保留、区域处理、子处理者和删除 SLA；境外传输在上线前完成适用路径和单独同意评估。
- 上传前用短而显著的告知说明处理目的、供应商类别、保存时长和删除；提供无需账号也能使用的删除请求凭证/通道。
- 不采集不必要的账号、精确位置、广告 ID；IP 日志缩短留存并限权。隐私承诺要与备份、监控和供应商真实能力一致。

**Warning signs:**
- 隐私文案写“我们不存储”，架构图却有对象存储、APM payload、供应商 retention 或人工排错队列。
- 团队无法回答图片在哪个国家/地区处理、供应商是否用于训练、多久彻底删除。
- 无账号用户没有删除请求渠道；数据留存写“视需要而定”。
- 为了“以后训练”默认无限期保留所有照片。

**Phase to address:**
**供应商选型与隐私设计阶段（签约/接 API 前）**；上线前完成 PIIA、文案、删除证明和跨境法律复核。

### Pitfall 9: 匿名、按次付费推理造成成本失控和 10 秒目标破产

**What goes wrong:**
大图上传、串行多模型调用、模型超时后无界重试、前端重复提交和恶意刷接口，导致 P90/P95 延迟超过 10 秒并产生不可控账单。供应商故障时所有请求继续堆积，恢复后形成重试风暴。

**Why it happens:**
免登录端点缺少用户级额度；图片 token/像素成本和延迟高度可变；把检测、识别、估重、解释拆成多个串行模型调用会叠加尾延迟。OWASP API4 将未限制执行时间、上传大小、调用频率和第三方支出列为资源消耗漏洞。

**How to avoid:**
- 浏览器先压缩，服务端再执行像素/字节上限；通过真实评测找出不损精度的最低分辨率，禁止原始 48MP 图直接进入模型。
- MVP 优先一次受约束的视觉调用 + 本地目录计算；只有评测证明收益时才增加分割/二次调用，并设置总 deadline。
- 端到端预算拆分：上传、预处理、供应商、校验、重算；持续观测 p50/p90/p95、超时率、每成功餐成本和各阶段 span。
- 请求使用幂等键；前端防双击；最多一次有抖动的有界重试，只重试明确可重试错误且受总 deadline 约束。设置并发隔离、队列长度、熔断和供应商降级。
- 匿名端点使用 IP + 短期设备/session 风险信号的分层限速、单请求/日额度、验证码升级策略；配置供应商硬预算、告警和 kill switch。
- 超时或供应商不可用时明确失败，不展示旧结果或编造降级结果；可保留手动菜名/克数计算路径。

**Warning signs:**
- 只测平均延迟，不测 90% 有效请求的端到端时延；本地 Wi-Fi 演示代替移动网络测试。
- 一个请求可触发 3 次以上串行模型调用，且每层 SDK 都自动重试。
- 没有每成功请求成本、失败请求成本、缓存命中率和供应商超时率看板。
- 任意脚本可无限调用匿名接口，预算只有邮件告警没有硬停止。

**Phase to address:**
**性能预算与滥用防护阶段**；必须在公开测试前用移动网络、并发和供应商故障注入验收 QLT-05。

### Pitfall 10: 精确数字、免责声明和健康话术共同制造误导

**What goes wrong:**
界面用大号“623 kcal”“237 g”和绿色“健康/适合减脂”传达确定性，误差范围藏在折叠区；底部一句“仅供参考”不能抵消主要视觉信息。用户可能据此进行严格热量控制、疾病饮食或进食障碍相关决策。营销又使用“精准识别”“科学减脂”“控糖/治疗”等无法由单图证实的表述。

**Why it happens:**
精确数字更像成品，增长文案偏好绝对承诺，但本产品的误差来自不可见变量而非普通四舍五入。中国《广告法》要求引用数据真实、准确并标明出处，且非医疗广告不得涉及疾病治疗功能或使用易与医疗混淆的用语。2025 年生效的 AI 生成合成内容标识规则还要求适用场景下对生成内容/交互添加标识；是否适用于本产品应在上线前做法律判断，不能忽略。

**How to avoid:**
- 结果主视觉同时展示中心估计和同等醒目的合理区间，标注“按常见做法估算”；克数按可解释粒度取整。
- 在每项旁显示误差来源（份量、配方/用油、识别）和可执行修正，不能只放全局免责声明。
- 禁止“精准、准确到克、AI 称重、保证减脂、控糖治疗、替代营养师”等表述；不提供疾病、孕产、儿童或进食障碍建议。
- 所有准确率与覆盖率营销声明绑定具体测试范围、样本量、日期、目标 100 菜和指标定义；不得把 Top-3 写成“识别准确率”。
- 法务复核《广告法》、隐私告知和 AI 生成内容标识适用性；界面至少清楚说明结果由 AI 辅助估算，营养值来自受控目录。
- 做理解性测试：用户应能复述“这是范围而非称重结果、隐藏油糖不可见、可手动修改”。

**Warning signs:**
- 用户测试中多数人只记住单个 kcal 数，不知道区间代表什么。
- 营销页准确率没有数据集、样本量、时间和指标定义。
- “仅供参考”字号远小于中心值；修正入口难找。
- 产品团队把免责声明当作可以继续展示虚假精度的许可证。

**Phase to address:**
**结果 UX 与合规文案阶段**，并在**上线门禁**进行法务复核和用户理解测试。

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| 让 VLM 直接返回 kcal | 原型快 | 不可审计、无法重算、模型升级即漂移 | 仅一次性探索，不进入产品分支或正式评测 |
| 每道菜只存一个 kcal/100 g | 数据简单 | 隐藏配方误差无法校准，区间虚假 | 仅用于 UI 原型占位，必须显著标记 synthetic |
| 随机按图片切 train/test | 一行代码 | 同订单/商家泄漏，指标虚高 | 永不用于里程碑验收 |
| 用模型自报 confidence | 无需校准集 | 过度自信、阈值无业务含义 | 仅日志观察，不展示、不驱动候选 |
| 使用模型“latest”别名 | 自动升级 | 行为和成本无预警改变，无法复现 | 仅非生产探索环境 |
| 原图长期保存以便“未来训练” | 将来可能有数据 | 隐私、授权、泄露面和删除成本激增 | 仅单独 opt-in、固定用途/期限的研究样本库 |
| 只做前端压缩和限流 | 实现容易 | 可被绕过，后端成本/安全无保护 | 永不作为唯一控制 |
| 用统一 ±20% 区间 | UI 简单 | 高油菜覆盖不足、低风险菜过宽 | 仅早期原型，不可对外宣称覆盖率 |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| 多模态模型 API | 把 schema 合规当语义正确；多层自动重试 | 固定版本、确定性字段验证、一次有界修复、总 deadline、记录 request ID |
| 境外模型/云服务 | 未核实训练使用、保留、人工审阅、处理地域和子处理者 | 数据流/PIIA、委托处理条款、跨境路径和必要同意先于上线 |
| 对象存储/CDN | 公共 URL、生命周期只删原图不删派生物 | 私有桶、短 TTL、随机键、无缓存或短缓存、全链路删除验证 |
| USDA FoodData Central | 前端暴露 API key；把美式成菜直接匹配中式菜 | 服务端访问或版本化离线镜像；只用于适配的基础食材并保留来源 |
| 中国食物成分数据 | 把官方推荐引用误认为开放商用授权 | 取得书面许可/法律确认，建立字段级来源和版本台账 |
| 日志/APM/错误追踪 | 自动采集图片、base64、签名 URL 和完整模型响应 | payload denylist、字段化错误码、短留存、抽样且去标识化 |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| 原始高分辨率图片直传模型 | 上传慢、图像 token/费用波动、移动端失败 | 客户端压缩 + 服务端像素上限；用精度-分辨率曲线选档 | 低端机/4G 即可暴露，不必等规模 |
| 串行“分割→识别→估重→解释” | 平均勉强，P90 超 10 秒 | MVP 单调用；并行可并行项；共享总 deadline | 供应商 P95 抖动时立即失败 |
| 每层 SDK/网关都自动重试 | 重复计费、恢复时流量倍增 | 统一重试所有权、幂等键、最多一次、指数退避 + jitter | 供应商部分故障时 |
| 匿名接口仅按 IP 粗限流 | NAT 用户误伤，攻击者易换 IP | IP + session/设备风险信号、并发/日额、异常挑战 | 公开 URL 被爬虫发现后 |
| 无限排队等待模型恢复 | 内存/队列膨胀、结果过时 | 有界队列、过期丢弃、熔断、手动降级 | 几分钟供应商故障即可 |
| 只监控请求成本 | 失败/重试掩盖真实单位经济 | 监控每**成功餐**成本、每阶段延迟、失败原因 | 首次真实流量就会误判 |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| 信任扩展名或 `Content-Type` | 畸形/非图片进入解析器 | magic bytes + 安全解码重编码 + 格式 allowlist |
| 只限制文件字节，不限制像素/帧 | 解码炸弹导致内存/CPU DoS | 最大像素、长宽比、帧数、CPU/内存/时间隔离 |
| 保留 EXIF 和原文件名 | 泄露定位、设备和路径信息 | 入口剥离全部元数据、生成随机键 |
| 原图/签名 URL 进入日志 | 内部人员或日志系统扩大泄露面 | payload 屏蔽、短留存、访问审计 |
| VLM 可调用工具或自由写数据库 | 图片提示注入扩大为数据/权限事故 | 模型零权限，代码层白名单和边界校验 |
| 无滥用预算/kill switch | 刷量变成直接财务损失 | 多维限流、并发限制、硬预算、异常熔断 |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| 中心值醒目、区间弱化 | 把估算当测量 | 同屏同权展示中心 + 区间 + “常见做法估算” |
| 为每项显示个位数克重 | 制造不存在的精度 | 合理取整，直接可编辑 |
| 低置信仍默认唯一菜名 | 用户不知道该修正 | 展示 2–3 候选和明显“不确定”状态 |
| 错图只报“识别失败” | 用户无法改进输入 | 指出过暗/模糊/遮挡/非食物，并给重拍动作 |
| 区间很宽但不解释原因 | 用户认为系统没用 | 分解“份量/配方/用油”误差，并提供高价值修正 |
| 修改后只改总数 | 用户无法理解影响 | 明细和总计即时、确定性重算，突出变化来源 |
| 用健康颜色或标签评价食物 | 引发道德化/医疗化解读 | 只陈述估算数据和不确定性，不做“健康/不健康”判决 |

## "Looks Done But Isn't" Checklist

- [ ] **多菜识别：** 不只是主菜分类；验证实例级召回、漏项和重复项。
- [ ] **100 道目录：** 每道菜有同义词、OOD 行为、来源、单位热量分布和版本，不是一张名称表。
- [ ] **估重：** 有真实称重、P90 和分层误差；不是模型给出一个 grams 字段。
- [ ] **热量区间：** 用独立数据校准，同时验覆盖率和宽度；不是固定百分比。
- [ ] **真实热量：** 包括原料、烹调油和调味品的可追溯计算；不是目录中心值自证。
- [ ] **候选置信：** 阈值经独立校准；不是模型 verbalized confidence。
- [ ] **结构化输出：** 通过语义白名单、范围、去重和重算测试；不只是 JSON 可解析。
- [ ] **图片删除：** 原图、派生图、CDN、队列、日志、备份和供应商侧均验证；不只是数据库删行。
- [ ] **图片安全：** 畸形格式、超大像素、多帧、提示注入和非食物攻击集通过。
- [ ] **隐私告知：** 写清处理目的、地域、供应商类别、期限和删除通道，并与真实架构一致。
- [ ] **性能：** 在目标移动网络与并发下达到端到端 P90 ≤ 10 秒，包含失败和重试。
- [ ] **成本：** 有每成功餐成本、硬预算、限流、熔断和 kill switch。
- [ ] **健康表述：** 用户理解测试和法务复核通过；无精确/医疗/减脂保证。
- [ ] **AI 标识：** 已书面判断现行生成合成内容标识规则是否适用并落实要求。

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| 识别指标因漏项虚高 | MEDIUM | 暂停扩菜；重标实例；新增召回/重复指标；重选 prompt/模型 |
| 克数无可用精度 | HIGH | 降级为份量档位/用户编辑；采集称重与容器数据；重新校准 |
| 隐藏油糖导致区间失真 | HIGH | 撤下窄区间和准确率宣传；按烹饪法/商家补配方样本；重建区间 |
| 营养数据授权不清 | HIGH | 立即隔离/下线相关数据；替换为 CC0/自建授权数据；重算并记录版本 |
| 测试集泄漏/磨损 | HIGH | 作废分数；按订单/商家去重重切；采集全新封存外部集 |
| 图片隐私泄露 | HIGH | 停止上传；吊销 URL/密钥；全链路删除；按 PIPL 评估通知与补救；完成复盘 |
| 上传解析漏洞 | HIGH | 关闭受影响格式；隔离处理器；升级/替换库；加入恶意样本回归 |
| 成本/重试风暴 | MEDIUM | 启用 kill switch；熔断供应商；清理过期队列；修复幂等和重试所有权 |
| 模型版本漂移 | MEDIUM | 回退固定快照；恢复旧 prompt/schema；跑封存回归后再升级 |
| 误导性健康文案 | MEDIUM/HIGH | 立即撤下声明；保存证据和影响范围；修正文案/UI；法务复核后恢复 |

## Pitfall-to-Phase Mapping

| Pitfall | Prevention Phase | Verification |
|---------|------------------|--------------|
| 数据授权与来源不可追溯 | Phase 1：数据权利与合规地基 | 100% 条目有许可、来源、版本、计算链；未决来源不上线 |
| 评测泄漏和指标自欺 | Phase 2：真实数据与评测契约 | 按订单/商家分组、近重复审计、封存集、指标定义冻结 |
| 多菜漏检/OOD 强猜 | Phase 3：识别与输出契约 | 实例 F1、漏项/重复/OOD 拒识、Top-1/Top-3 分层达标 |
| 单图估重伪精确 | Phase 3：估重模型与校准 | MdAPE ≤25% 且 P90/偏差可接受；跨视角稳定性测试 |
| 隐藏油糖与配方差异 | Phase 3：营养区间建模 | 总热量覆盖 ≥80%，并限制宽度；高油菜分层覆盖达标 |
| JSON 正确但语义错误 | Phase 3：推理契约 | 模糊测试、范围/白名单/去重、确定性重算、版本回归 |
| 图片上传和提示注入 | Phase 4：图片入口与安全 | 恶意文件、解码炸弹、图中指令、非食物测试全部 fail closed |
| 图片隐私、供应商和跨境 | Phase 4：隐私工程 | PIIA、委托条款、告知/同意、TTL 与全链路删除演练 |
| 虚假精度和健康误导 | Phase 5：结果 UX 与修正 | 用户能解释区间和误差；法务/AI 标识检查；修改即时重算 |
| 延迟、刷量和账单风险 | Phase 6：生产可靠性 | 移动网络并发下 P90 ≤10s；故障注入、硬预算、熔断/降级通过 |

## Phase Ordering Implication

1. **先解决权利与真值，再选模型。** 没有合法营养源、称重/配方真值和冻结评测协议，任何模型对比都是噪声。
2. **先校准识别、估重和区间，再做“漂亮结果页”。** UI 若先固定，会反向迫使团队用虚假精度填满设计。
3. **图片入口与隐私必须早于真实公测。** 安全重编码、元数据剥离、供应商地域/留存和删除链不能在收到用户图片后补。
4. **最后才做规模化可靠性。** 但延迟/成本预算要在模型选型时记录，否则最后才发现链路无法满足 10 秒和单位经济。
