# Requirements: 中式外卖热量识别

**Defined:** 2026-08-26
**Core Value:** 让普通用户在约 10 秒内得到一份可信且可修正的中式外卖整餐热量估算。

## v1 Requirements

### 图片输入

- [ ] **IMG-01**：用户无需登录即可在移动端拍照或从设备上传一张图片。
- [ ] **IMG-02**：用户上传的图片会经过格式、文件大小、像素、解码安全和基础画质检查。
- [ ] **IMG-03**：图片模糊、过暗、不是食物或无法安全分析时，用户会看到明确且可操作的重拍提示。

### 菜品识别

- [ ] **REC-01**：用户可以在一张外卖套餐图片中分别得到多个可见菜品的识别结果。
- [ ] **REC-02**：识别结果会归一化到约 100 道受控中式外卖菜目录。
- [ ] **REC-03**：目录外或无法确认的菜品会显示为不支持或无法确认，而不是被强行猜成目录内菜品。
- [ ] **REC-04**：每个识别项会显示具体菜名和估算克数。
- [ ] **REC-05**：低置信度识别项会提供 2–3 个目录内候选菜名供用户选择。

### 热量结果

- [ ] **CAL-01**：每个菜品的热量由有来源记录的受控营养数据计算，不采用模型自由生成的热量值。
- [ ] **CAL-02**：每个菜品会显示估算克数、中心热量和合理范围。
- [ ] **CAL-03**：整餐会显示中心热量和合理范围。
- [ ] **CAL-04**：结果页会明确说明配方、用油、糖、酱汁和实际份量会造成估算误差。

### 用户修正

- [ ] **EDIT-01**：用户可以精确修改每个菜品的克数。
- [ ] **EDIT-02**：用户可以切换候选菜名，或搜索并替换为受支持的菜名。
- [ ] **EDIT-03**：用户可以删除误识别项。
- [ ] **EDIT-04**：修改菜名、克数或删除项目后，单项和整餐结果会立即重算，且不会再次调用视觉模型。

### 状态与失败恢复

- [ ] **FLOW-01**：用户可以看懂图片准备、上传、分析和完成状态。
- [ ] **FLOW-02**：超时、限流、服务错误和模型输出异常会显示明确的恢复或重试操作。
- [ ] **FLOW-03**：重复点击、重试和网络抖动不会产生重复分析任务或重复模型费用。

### 隐私与安全

- [ ] **SAFE-01**：用户在上传前可以看到图片的第三方处理、留存和删除说明。
- [ ] **SAFE-02**：原始图片只用于当次分析，分析完成后删除，不长期保存。
- [ ] **SAFE-03**：服务端会剥离图片元数据，并拒绝伪造格式、解码炸弹、超大像素和其他危险图片。
- [ ] **SAFE-04**：匿名分析接口具有限流、并发限制、费用硬上限和紧急熔断能力。

### 数据与可追溯性

- [ ] **DATA-01**：约 100 道目标菜拥有稳定 `dishId`、别名、标准配方、营养范围、来源和授权记录。
- [ ] **DATA-02**：模型、提示词、图片预处理、菜品目录、营养数据和计算规则具有版本标识，使分析结果可复现。
- [ ] **DATA-03**：数据库保存匿名结构化分析结果、模型运行元数据和用户修正，以支持评测和改进。
- [ ] **DATA-04**：营养数据缺少明确商业使用权或可追溯推导链时，系统不得公开上线。

### 工程架构

- [ ] **ARCH-01**：仓库包含独立的 `frontend/` 和 `backend/` 项目。
- [ ] **ARCH-02**：前端使用 React、TypeScript 和 Vite，并通过 REST API 调用后端。
- [ ] **ARCH-03**：后端使用 FastAPI、Python、SQLAlchemy 2 和 Alembic。
- [ ] **ARCH-04**：PostgreSQL 保存菜品、别名、标准配方、营养数据和数据版本。
- [ ] **ARCH-05**：前后端通过版本化 OpenAPI 契约协作。
- [ ] **ARCH-06**：本地开发者可以通过 Docker Compose 启动 PostgreSQL 和所需本地依赖。

### 质量与发布门槛

- [ ] **QLT-01**：目标菜品 Top-1 识别准确率达到 85% 或以上。
- [ ] **QLT-02**：正确菜名出现在前三候选中的比例达到 95% 或以上。
- [ ] **QLT-03**：单项克数估算的中位相对误差不高于 25%。
- [ ] **QLT-04**：真实整餐热量落入系统合理区间的比例达到 80% 或以上，并同时满足区间宽度护栏。
- [ ] **QLT-05**：90% 的有效识别请求在目标移动网络环境下于 10 秒内返回结果。
- [ ] **QLT-06**：用户从上传图片到理解结果的主流程不超过 3 次操作。
- [ ] **QLT-07**：发布候选版本通过冻结测试集、移动端端到端测试、恶意图片测试、费用上限和隐私删除链验证。

## v2 Requirements

### 产品扩展

- **V2-01**：用户可以查看蛋白质、脂肪和碳水化合物等宏量营养素。
- **V2-02**：用户可以提供第二视角或尺度参照物以改善估重。
- **V2-03**：用户可以自愿提交纠错反馈，帮助改进目录和模型。
- **V2-04**：用户可以生成不包含敏感信息的本地分享卡片。
- **V2-05**：系统可以在有真实需求和合法数据的前提下扩展菜品目录。
- **V2-06**：用户可以创建账号并查看历史分析记录。

## Out of Scope

| Feature | Reason |
|---------|--------|
| 覆盖所有中餐或全球食物 | 首版必须控制目录范围，避免以覆盖率牺牲准确性 |
| 模型自由生成菜名和营养值 | 结果无法校准、追踪或可靠复现 |
| 社区、排行榜和内容流 | 与快速了解一餐热量的核心价值无关 |
| 医疗、减脂或个性化治疗建议 | 超出产品定位且可能误导用户 |
| 长期保存原始图片 | 不符合数据最小化原则，且首版没有必要 |
| 微服务、消息队列和分布式任务系统 | 当前规模不需要；仅在真实延迟和可靠性数据证明必要时引入 |

## Definition of Done

- 所有 v1 需求均映射到且仅映射到一个路线图阶段。
- 每项需求完成实现、自动化验证及必要的人工移动端验收。
- 约 100 道菜的数据来源、授权和版本记录完整。
- 冻结测试集达到所有识别、估重、区间和延迟门槛。
- 原图删除链、日志脱敏、限流、费用上限和紧急熔断均经过验证。
- 产品文案不承诺称重级、医疗级或虚假的精确度。
