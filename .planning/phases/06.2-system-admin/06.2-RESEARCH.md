# Phase 06.2：系统管理与角色治理 — Research

## 结论

现有后端已经具备固定 `user/admin` 枚举、数据库实时管理员校验、首管理员 bootstrap、管理员晋升和不可变审计；缺口是公开账号治理 API、安全降权策略和独立后台 UI。最小正确实现应扩展既有 `admin` 模块，而不是新建平行权限系统。

## 现有能力与缺口

| 领域 | 已有能力 | 本阶段缺口 |
|---|---|---|
| 授权 | `AdminService.require_role` 每次查 PostgreSQL | 无账号列表与角色统计 API |
| 角色 | `UserRole.USER/ADMIN` 固定枚举 | 无后台升降权入口 |
| 审计 | `AdminRoleAudit`、`AdminAuditEvent` | HTTP 角色变更尚未接入幂等事件 |
| 并发 | bootstrap advisory lock、用户行锁 | 降权需复用事务锁并保护最后管理员 |
| 前端 | 独立 admin SPA、路由守卫、Zod + Query | 无系统管理导航与页面 |

## 推荐实现

- API 保持 `/api/v1/admin/*`，新增账号分页查询、固定角色列表、角色变更三个端点。
- Service 负责授权、目标校验、自操作限制、最后管理员保护、幂等与事务；Repository 只提供查询、锁和持久化。
- 不新增数据库表：现有用户角色列和两类审计表已能表达本阶段事实。
- 降权不撤销认证会话；所有后台请求继续实时查库，因此旧 token 也会立刻得到 403。
- 前端新增独立 `features/system/`，用严格 Zod DTO，禁止页面直接访问未校验响应。

## 风险

- 只在 UI 禁用自降权或最后管理员降权会被直接 API 调用绕过。
- 角色与审计分开提交会留下不可追溯的权限变化。
- 把固定角色伪装成可编辑权限矩阵会制造错误产品承诺。
- 降权后若只依赖 JWT role，会让旧 token 在过期前继续拥有后台权限。

## 验证策略

Fake repository 单测验证策略分支；HTTPX 验证公开错误码；真实 PostgreSQL 验证锁、事务、审计和会话语义；Vitest/MSW 验证页面交互；Playwright 与内置浏览器验证真实注册、登录、升权、角色页、降权和 403 路径。
