## Pattern Assignments

### Root bootstrap and developer contract

**Files:** `compose.yaml`, `.gitignore`, `README.md`, `frontend/.env.example`, `backend/.env.example`

**Analog:** none in repository. Use `01-CONTEXT.md` D-19, D-21–D-27 and `01-RESEARCH.md` “Recommended Project Structure”.

**Required pattern:** Compose exposes only a PostgreSQL `db` service on `5432` with a healthcheck. Frontend (`5173`) and FastAPI (`8000`) run in separate developer terminals. Do not hide migrations or seed work in application startup, and do not add pgAdmin as a runtime dependency.

**Copy-worthy upstream contract** (`01-CONTEXT.md` lines 47–53):

```text
Docker Compose 默认只启动 PostgreSQL。
Alembic migration 和菜品种子导入使用独立、显式命令；FastAPI 启动时不得自动建表、迁移或灌数据。
本地默认端口固定为 Vite 5173、FastAPI 8000、PostgreSQL 5432。
开发环境 CORS 只允许 http://localhost:5173，不得使用 *。
```

**Naming/configuration:** use `compose.yaml`; keep real `.env` ignored; examples contain keys and non-secret local values only. Frontend may expose only `VITE_API_BASE_URL`; backend owns `DATABASE_URL`, `TEST_DATABASE_URL`, and an explicit environment name. README must show this exact observable order: `docker compose up -d db` → migration → seed → backend terminal → frontend terminal.

### Frontend bootstrap, transport boundary, and page composition

**Files:** `frontend/src/main.tsx`, `frontend/src/App.tsx`, `frontend/src/routes/calculator-page.tsx`, `frontend/src/api/{http,dishes,calculations,types}.ts`

**Analog:** none in repository. Use the folder boundary from `01-RESEARCH.md` lines 221–258 and the REST contract from lines 319–334.

**Imports/bootstrap pattern:** `main.tsx` is the only place that mounts React and provides the `QueryClientProvider`; `App.tsx` only composes React Router; the route composes the calculator feature. Keep fetch and API DTO types in `src/api/`; no feature component constructs URLs or calculates kcal.

**Core request-response contract** (`01-RESEARCH.md` lines 321–334):

```text
GET  /api/v1/dishes?query=<1..50 chars>&limit=<1..20>
200  {"items":[{"dishId","name","matchedAlias","typicalServingGrams","dataStatus"}]}

POST /api/v1/calculations
body {"dishId":"...","grams":180}
200  {"dishId":"...","dishName":"宫保鸡丁","grams":180,"kcal":342}
```

**Error pattern:** `http.ts` converts a non-2xx response into one typed client error containing only safe API `code`, `message`, and optional field details. Hooks decide UI state; do not display raw FastAPI/Python exception text. Keep query errors and mutation errors separate.

**Naming:** API functions are verbs (`searchDishes`, `calculateCalories`), request/response interfaces use PascalCase (`DishSearchItem`, `CalculationRequest`), and JSON fields preserve the published camelCase contract. Do not create duplicated “frontend nutrition calculation” helpers; the backend response is the only authority.

### Frontend calculator feature and generated primitives

**Files:** `frontend/src/features/calculator/{CalculatorForm,DishSearchCombobox,GramsField,CalculationResult}.tsx`, `use-dish-search.ts`, `use-calculation.ts`, `src/components/ui/*`

**Analog:** no project component exists. The component primitive analog is the official shadcn Base UI CLI output; feature behavior comes from `01-UI-SPEC.md`.

**Generated component pattern:** first run the official Vite/Base UI shadcn initialization in `frontend/`, commit `components.json`, then add only `button`, `card`, `input`, `label`, `alert`, and `combobox`. Generated UI files remain thin library primitives; page-specific Chinese copy and query logic belong in `features/calculator/`.

**Core state boundary** (`01-UI-SPEC.md`, “Interaction and State Contract” and implementation notes):

```tsx
// Query: debounced GET search only.
const dishes = useDishSearch(query)

// Local-only form state. Selecting a dish replaces grams with
// typicalServingGrams; editing grams must not call POST.
const [grams, setGrams] = useState('')

// Mutation: invoked only from a valid form submit.
const calculation = useCalculation()
calculation.mutate({ dishId: selectedDish.dishId, grams })
```

**Accessibility/validation pattern:** `CalculatorForm` owns selected dish, raw grams string, client errors, successful result, and stale-result state. It validates selected dish plus `0 < grams <= 3000` before mutation, focuses the first invalid field, and must make **zero POST requests** on invalid input. `DishSearchCombobox` uses Base UI keyboard semantics; standard name is first line and alias match is a secondary line. Errors use visible text and `role="alert"`; success/loading use `aria-live="polite"`.

**UI contract to copy:** single mobile-first `<main lang="zh-CN">`, page gutter `16px`, maximum width `560px` at `640px+`, 44px minimum controls, 48px primary button, Slate/Teal palette, 8px radii. The only primary path is search/select → optional grams edit → calculate. Old results become visibly stale after any input change and must not retain accent emphasis.

**Explicit rejection:** Do not import `@headlessui/react`; that research example is superseded. Do not use native `select`, a background kcal calculation, automatic POST on grams changes, dark mode, image upload, intervals, source/license display, or multi-dish UI in this phase.

### Backend application bootstrap and HTTP layer

**Files:** `backend/app/main.py`, `app/api/v1/router.py`, `app/api/v1/dishes.py`, `app/api/v1/calculations.py`, `app/api/v1/errors.py`, `app/core/config.py`, `app/core/database.py`

**Analog:** none in repository. Use the strict boundary in `01-CONTEXT.md` lines 36–41 and the FastAPI dependency example in `01-RESEARCH.md` lines 260–280.

**Controller pattern** (upstream excerpt):

```python
@router.post("/calculations", response_model=CalculationResponse)
def calculate(
    payload: CalculationRequest,
    service: Annotated[CalculationService, Depends(get_calculation_service)],
) -> CalculationResponse:
    return service.calculate(payload)
```

**Boundary rule:** routers parse/query parameters, inject a service, set `response_model`, and translate known domain failures into the project’s structured HTTP error envelope. They contain no `select()`, ORM model, `Session`, `commit()`, calorie formula, seed logic, or policy decision. This is not optional architecture polish; D-14/D-15 lock it.

**Bootstrap/error patterns:** `main.py` creates the FastAPI app, installs explicit `CORSMiddleware` for only `http://localhost:5173`, registers the `/api/v1` router and exception handler, and leaves `/docs`/`/openapi.json` at FastAPI defaults. `config.py` is the sole settings reader/validator. `database.py` owns engine/sessionmaker and an injected request-scope session:

```python
engine = create_engine(settings.database_url, pool_pre_ping=True)
SessionLocal = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)

def get_session() -> Generator[Session, None, None]:
    with SessionLocal() as session:
        yield session
```

No startup `create_all`, Alembic upgrade, or seed execution. Never log secrets, images, base64, full model output, or a database URL.

### Backend persistence models, schema DTOs, repositories, and services

**Files:** `app/models/*`, `app/schemas/*`, `app/repositories/{dish_repository,catalog_repository}.py`, `app/services/{dish_service,calculation_service,release_policy}.py`

**Analog:** none in repository. Follow `01-RESEARCH.md` lines 260–341 exactly as the first in-repo convention.

**Dependency direction:**

```text
api/v1 → services → repositories → models
              ↑
           schemas (public API DTOs only)
core supplies settings and request-scoped database sessions
```

No inner module imports a router. Pydantic schemas and SQLAlchemy models are separate even when fields initially look similar. Public API never serializes an ORM instance directly.

**Model/repository pattern:** model modules use singular class names and plural table names: `DataVersion`/`data_versions`, `Dish`/`dishes`, `DishAlias`/`dish_aliases`, `StandardRecipe`/`standard_recipes`, `NutritionRecord`/`nutrition_records`. Public stable `dish_id` is not the internal surrogate primary key. Use PostgreSQL `NUMERIC`/Python `Decimal` for grams and calories; establish database constraints for unique stable IDs and normalized aliases, positive grams/kcal values, enum release status, plus the recipe/nutrition/version foreign keys. Repository methods expose intent (`search_by_normalized_text`, `get_calculable_dish`, `upsert_catalog`) and only execute persistence queries.

**Service/calculation pattern:** services accept a repository interface/protocol so unit tests can pass fakes. `DishService` maps search matches into public DTOs. `CalculationService` validates that the dish exists and has a locally eligible controlled nutrition record, then owns one deterministic formula and fixed rounding rule:

```python
def kcal_for(grams: Decimal, kcal_per_100g: Decimal) -> int:
    return int((grams * kcal_per_100g / Decimal("100")).quantize(
        Decimal("1"), rounding=ROUND_HALF_UP
    ))
```

Only repository-fetched controlled data enters the formula. The request must reject client-provided kcal, nutrition-per-100g, source, or license fields. `ReleasePolicy` makes `demo_only` versus `production_approved` executable: production preflight fails on any served record lacking approval, source, license/commercial-use reference, or derivation chain.

**Schema naming:** Pydantic classes describe the contract, e.g. `DishSearchItem`, `DishSearchResponse`, `CalculationRequest`, `CalculationResponse`, and `ErrorResponse`; Python attributes may be snake_case internally but must serialize the locked `dishId`, `dishName`, `typicalServingGrams` contract through explicit aliases/configuration. `CalculationRequest.grams` is a bounded `Decimal`, not a float.

### Migration, source manifest, seed and release commands

**Files:** `backend/alembic/env.py`, `backend/alembic/versions/<revision>_initial_catalog.py`, `backend/data/catalog/v1.json`, `backend/app/scripts/{seed_catalog,release_preflight}.py`

**Analog:** none in repository. Use `01-RESEARCH.md` “Pattern 3: Explicit schema migration plus idempotent seed” (lines 290–307) and “Pattern 4: Data eligibility policy is executable” (lines 308–317).

**Command pattern:** the first Alembic revision contains DDL only: tables, indexes, FK/unique/check constraints, and the release-status type. It must not contain the business catalog. `seed_catalog` reads the versioned manifest, validates every record, upserts by stable external IDs in one transaction, emits a non-sensitive import summary, and rolls back the complete operation on one invalid record. Begin with D-08’s 15 dishes to validate the schema, then expand the same manifest to roughly 100 before phase completion.

**Preflight pattern:** `release_preflight --environment production` validates both the manifest and current DB. It returns a machine-readable report and non-zero status for any served/unapproved/demo data or missing provenance/license/derivation evidence. Local development may use `demo_only`, but no production deployment path may skip the preflight.

**Naming:** use a stable file such as `v1.json`, a descriptive immutable revision such as `20260826_0001_initial_catalog.py`, module commands runnable as `python -m app.scripts.seed_catalog` and `python -m app.scripts.release_preflight`. The revision ID format is discretionary, but revision files are immutable after review.

**PostgreSQL isolation pattern** (`01-RESEARCH.md` lines 477–491):

```python
connection = engine.connect()
outer_transaction = connection.begin()
session = Session(bind=connection, join_transaction_mode="create_savepoint")
try:
    yield session
finally:
    session.close()
    outer_transaction.rollback()
    connection.close()
```

Use a dedicated `TEST_DATABASE_URL`; a test that points at `DATABASE_URL` or `sqlite://` is wrong and must fail setup rather than silently proceed.

**Frontend test division:** feature tests use Vitest + Testing Library + user-event and mock the API boundary, not `fetch` scattered through components. Playwright owns one browser thin-slice flow. A human must verify the official Vitest package before installation, because research recorded a heuristic false-positive flag.

## Shared Patterns

### One calculation authority

**Apply to:** API DTOs, `CalculationService`, frontend API client, calculator feature, tests.

```text
Browser sends only stable dishId + grams.
FastAPI service loads controlled nutrition data.
Backend computes and rounds kcal.
Browser renders backend kcal and never reimplements the formula.
```

This prevents formula drift and directly enforces `CAL-01` plus `AGENTS.md`’s single-source-of-truth rule.

### Boundary and dependency injection

**Apply to:** every backend endpoint and test.

```text
API handles HTTP → Service owns rules → Repository owns SQLAlchemy → Model owns mapping.
Schema is DTO boundary, not a replacement for Model.
```

Service unit tests inject fake repositories. Repository integration tests use isolated PostgreSQL. Router tests assert schemas/status/error envelopes.

### Data qualification and privacy

**Apply to:** models, seed manifest, seed command, preflight, API response filtering, docs, tests.

Keep source, license, version, and release status in PostgreSQL and return `dataStatus` where the API contract calls for it. Do not put provenance fields into Phase 1 UI. Never store or log original images, base64, full model responses, credentials, or DB URLs.

### Error contract

**Apply to:** FastAPI exception mapping, API client, calculator form, API tests.

Use safe structured errors (`code`, user-safe `message`, optional field details). Treat malformed request/validation, missing dish, and ineligible data as explicit client-visible failure categories; reserve generic 5xx for unexpected faults. The browser maps safe field errors to controls and falls back to UI-spec Chinese copy for network/unknown failures.
