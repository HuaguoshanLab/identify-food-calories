## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01 受控相关范围：** 非精确召回允许同义名、地域修饰、相近做法和同类成品菜；不得仅因共享一个食材就召回完全不同的菜品。
- **D-02 分层排序：** 候选关系按“同一道菜的名称变体 → 地域/做法变体 → 同类成品菜”分层；向量相似度只能在同一关系层内参与排序，不能越层压过更直接的关系。
- **D-03 不凑满 Top 3：** 可靠候选不足 3 个时有几个返回几个；低质量候选不得为了填满列表进入结果。
- **D-04 用户可理解的原因：** 候选显示简短关系标签，例如“名称相近”“地域/做法变体”“同类食物”，并复用现有做法、份量或来源信息；不得向用户暴露内部相似度分数。
- **D-05 分阶段生效：** 新菜发布后，精确名称和模糊文本检索立即生效，语义索引异步补齐。
- **D-06 索引失败不回滚发布：** Embedding 生成失败不回滚已经有效的目录发布；系统执行有限自动重试，在后台显示索引状态，并允许管理员手动重试。
- **D-07 资格实时生效：** 菜品失格或撤销后，所有召回通道必须通过 PostgreSQL 当前资格条件立即排除它；派生向量和索引记录可稍后物理清理。
- **D-08 版本原子切换：** 新目录版本发布后，精确和文本搜索原子切换到新版本，旧版本立即退出新的搜索结果；已有历史快照保持不变，新版本语义索引异步补齐。
- **D-09 Provider 边界：** Embedding 使用可替换 Provider，生产默认 DashScope，测试只使用 Fake Provider；Agent 图不得直接调用 Embedding SDK。
- **D-10 最小化输入：** 只向 Embedding Provider 发送规范化后的单项菜名，不发送完整餐食描述、份量、用户身份、身体数据或健康数据。
- **D-11 向量空间升级：** 模型或维度升级时并行构建新索引；新索引完整且冻结评测通过后才能原子切换。不同模型或维度的向量严禁混合检索。
- **D-12 不持久化用户查询向量：** 用户查询文本和查询向量不得持久化，最多在当前 Agent 运行内复用；数据库只保存受控目录条目的向量。
- **D-13 显式启动：** Langfuse 只在显式运行混合检索实验时通过独立 Docker Compose 启动。应用日常启动、普通测试和 CI 确定性门禁均不得依赖 Langfuse。
- **D-14 保留 30 天：** Langfuse 中逐例 Trace 和 Score 保留 30 天；Git 永久保存冻结数据集、汇总报告及其 dataset、代码、检索和 embedding 版本 hash。
- **D-15 失败记录同等保留：** 成功和失败实验都保留 30 天，不隐藏或删除失败结果来改变结论；发布报告必须如实保留 FAIL。
- **D-16 显式发布：** 本地评测默认只生成本地报告，只有传入明确参数（例如 `--publish-langfuse`）才写入 Langfuse；发布前必须通过字段 allowlist 校验。

### the agent's Discretion

- PostgreSQL 模糊文本实现、阈值和索引选择，例如 `pg_trgm`、归一化策略及其阈值；最终参数必须由冻结数据集校准。
- 文本和向量通道的候选池大小、融合公式、稳定 tie-breaker 和关系层判定实现，但必须满足 D-01 至 D-04 及确定性顺序要求。
- 派生向量表、索引状态表、任务租约、outbox、重试次数和退避参数的具体 schema 与机制；必须保持 Alembic 单一 head。
- DashScope 的具体 embedding 模型、向量维度、超时与成本上限；必须有明确版本标识并能使用 Fake Provider 完成测试。
- Langfuse 独立 Compose 的具体服务拓扑、保留策略执行方式、实验命名和安全投影字段；不得与业务 PostgreSQL 共库或突破数据最小化边界。
- 后台索引状态和手动重试复用现有管理能力的具体 API/页面落点；不进行前端重设计。

## Summary

当前实现只具备“受控名称唯一精确可通过”的雏形，并不具备合格的模糊搜索：`SqlAlchemyNutritionRepository.search_qualified_foods()` 先做 `contains`，随后又在 Python 中只保留 alias 完全相等项；`NutritionService.search_food_catalog()` 是同步方法且没有匹配通道、关系层、检索版本或降级状态。更关键的是，餐食分析图会调用该搜索，饮食规划图和 `PlanningToolAdapter` 目前完全没有食品搜索能力。因此本阶段不是单纯“加一条向量 SQL”，而是一次跨 nutrition service/repository、provider、发布生命周期、两个 Agent 图、后台管理和评测链路的纵向改造。[VERIFIED: codebase — `backend/app/nutrition/{service,repository,schemas}.py`, `backend/app/agent/{tools,graph}.py`]

数据库已经启用 pgvector，但现有两张 embedding 表固定为测试性质的 `vector(3)`，且查询仍是 `ILIKE`；它们承载用户餐史/知识检索语义，不能拿来混存 1024 维菜品目录向量。当前 Alembic 是线性单 head `0024`，测试 PostgreSQL 的 pgvector 为 0.8.6，尚未安装 `pg_trgm`。应新增独立、可重建的目录向量空间和 durable embedding job 表，由 `0025` 一次迁移交付；发布事务只入队，外部 Provider 调用由有租约、幂等和有限重试的后台 worker 完成。[VERIFIED: codebase + live test DB — `backend/migrations/versions/0008_retrieval_vectors.py`, Alembic heads/history, `pg_extension`]

唯一可接受的在线顺序是：规范化 → current-qualified 唯一 canonical/alias 精确查询 → 唯一时立即 `PASS` → 否则文本召回 → 尝试临时查询向量和向量召回 → 统一资格物化 → 分层、去重和确定性排序 → 0–3 个候选且始终 `ASK`。Langfuse 只能镜像仓库评测。官方文档确认，Langfuse OSS 自托管没有内置自动数据保留（内置 retention 是 Enterprise 功能），因此 30 天合同必须通过显式 Public API 批量删除旧 traces/scores并回查确认，或使用可丢弃实例；不能虚构一个 OSS retention 环境变量。[CITED: https://langfuse.com/docs/administration/data-retention] [CITED: https://langfuse.com/docs/administration/data-deletion]

**Primary recommendation:** 先锁定搜索 DTO/唯一精确不变量、版本空间和冻结评测，再实现 `pg_trgm + pgvector`；随后接入异步索引生命周期与两个 Agent 流程，最后加后台状态、Langfuse 可选镜像和真实浏览器验收。

### Pattern 1: Exact-first authorization gate

**What:** 精确不是一个“分数更高的召回通道”，而是唯一能授予 `PASS` 的独立授权门。精确查找要同时覆盖 normalized canonical 和 controlled alias，并以不同 `food_id + catalog_version` 计数；0 或 >1 条都不得 PASS。[VERIFIED: SPEC]

```python

exact = repository.find_current_qualified_exact(normalized_query)
if len(exact) == 1:
    return FoodSearchResult(action="PASS", selected_food=exact[0], candidates=[])

# only this branch may call the embedding provider
return await search_non_exact_candidates(normalized_query)
```

### Pattern 2: One authoritative eligibility relation

**What:** exact、trigram 和 vector SQL 都从同一个 current-qualified CTE/subquery 出发；向量表只提供距离，不能独立决定条目仍有效。最终返回前再次以 `food_id + catalog_version` 物化权威 DTO。[VERIFIED: existing `_eligible_publication_statement` + SPEC]

**Why:** 删除旧向量是 eventually consistent；实时 SQL predicate 才能让撤销/失格即时生效。[VERIFIED: CONTEXT]

### Pattern 3: Versioned vector-space pointer

**What:** 向量行绑定 `food_id`、`catalog_version`、`normalized_name_hash`、`embedding_model`、`embedding_dimension`、`vector_space_version`；另用单行 active pointer 原子切换可搜索空间。HNSW 索引按空间/维度隔离，禁止一列混存不可比较模型。[VERIFIED: D-11]

1024 维低于 pgvector `vector` 的 2000 维 HNSW 上限；使用 `VECTOR(1024)` 和 `vector_cosine_ops` 是受官方支持的 SQLAlchemy 模式。[CITED: https://github.com/pgvector/pgvector] [CITED: https://github.com/pgvector/pgvector-python/blob/v0.5.0/README.md]

### Pattern 4: Durable outbox/lease worker

**What:** publication 事务写 `pending` job；worker 以 `FOR UPDATE SKIP LOCKED` 或等价 claim 取得短租约，事务外调用 Provider，回写时重检 job ownership/current state；失败只记录安全 error code、增加 attempt 和 `not_before`，达到上限进入 `failed`，管理员可审计地重置为 pending。[VERIFIED: existing memory provisioning pattern]

**Required invariants:** 同一 publication/name/vector space 唯一；重复 worker 幂等；过期 lease 可回收；旧空间任务完成也不能推进 active pointer；发布成功不依赖 Provider。[VERIFIED: D-05/D-06/D-11]

### Pattern 5: Conservative deterministic fusion

**What:** 通道先各自产生固定候选池，再按关系层排序；同一 `food_id + catalog_version` 去重。推荐 key：`relation_layer ASC, fused_rank DESC, normalized_name ASC, food_id ASC, catalog_version ASC`。向量分只在同层使用。[VERIFIED: D-02]

**Relation policy:** controlled canonical/alias 的 fuzzy 命中可标“名称相近”；只有版本化的受控 relation metadata/rule 明确证明地域或做法关系时才标“地域/做法变体”；纯 semantic 近邻保守标“同类食物”。不得凭向量距离推断关系类别。当前 schema 没有 relation metadata，因此规划必须增加受控、可版本化的关系证据或明确可审计规则，并用冻结集校准。[VERIFIED: codebase] [ASSUMED: recommended conservative mapping]

### Pattern 6: Async without leaking sync Session

**What:** Search Service/Tool 对图暴露 async。现有 SQLAlchemy 仍是 sync；若用 `asyncio.to_thread`，线程内创建和关闭短生命周期 Session，不把 request Session 传到线程。DashScope 使用 awaitable HTTPX client，不在 event loop 内 `asyncio.run()`。[VERIFIED: codebase architecture] [CITED: https://www.python-httpx.org/async/]

### Pattern 7: Langfuse as a post-report mirror

**What:** evaluator 先在完全无 Langfuse 环境生成并签定 `release.json`，publisher 只接受该报告和合成 case 的 allowlist projection；`--publish-langfuse` 才连接。Experiment name 包含 retrieval version + dataset hash 短码；metadata 保存完整 hashes，六项 score 保留明确 FAIL。[VERIFIED: D-13..D-16]

Langfuse Experiment SDK 在执行时使用 Langfuse 中 dataset 的最新版本，因此 Git dataset hash 仍须作为权威版本，publisher 必须校验/同步 items 并把 hash 写入每次 run，不能把 Langfuse 的“latest”当作冻结版本。[CITED: https://langfuse.com/docs/evaluation/experiments/data-model] [CITED: https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk]

### Anti-Patterns to Avoid

- **把所有通道塞进一条 weighted score SQL：** 会模糊唯一 exact 的授权边界，也容易让 vector 分越层覆盖名称关系。
- **先向量召回再在 Python 过滤资格：** 会泄露旧版/失格条目且 under-fill 不可控；资格必须下推到物化 SQL。
- **复用现有 `vector(3)` 表：** 语义、维度、隐私范围和生命周期都不同，混用就是数据模型错误。
- **发布事务中调用 DashScope：** 外部超时会扩大锁和回滚已经合格的 publication，直接违反 D-06。
- **仅补 `PlanningToolAdapter` 测试、不补图路径：** 这只能证明接口存在，不能证明饮食规划真实执行 `ASK/resume`。
- **catch `Exception` 后静默空结果：** Provider/DB 可预期故障应安全降级，编程错误/Pydantic invariant 仍要显式失败并告警。
- **把 Langfuse 放进应用 compose 默认依赖：** 会破坏离线启动、普通测试和 CI 独立性。
- **直接删 Langfuse 数据库表实现 retention：** 绕过其数据关系和删除语义；使用官方 API 并回查。

## Common Pitfalls

### Pitfall 1: canonical exact 被 alias 实现吞掉
**What goes wrong:** 当前代码主要围绕 alias membership；若 canonical 未重复写入 alias，“米饭”可能不是唯一 exact。  
**How to avoid:** SQL 显式比较 normalized canonical **OR** controlled alias；按 distinct identity 计数，测试 canonical-only、alias-only、重复 alias 和两个条目同名。[VERIFIED: codebase]

### Pitfall 2: HNSW filtering under-return
**What goes wrong:** approximate index 先取邻居、再过滤 active/eligible 时可能少于期望候选。  
**How to avoid:** 查询从 eligibility relation 出发，设置充足 pool；pgvector 0.8 可用 iterative scan，冻结评测同时与关闭 index scan 的 exact search 比较 recall。最终 Top 3 仍由确定性 Python/SQL key 排序。[CITED: https://github.com/pgvector/pgvector]

### Pitfall 3: 中文短词的 trigram 质量不稳定
**What goes wrong:** 很短的规范化菜名 trigram 数少，阈值复制英文经验会漏检或泛化。  
**How to avoid:** exact 单独处理；同时评估 `similarity`/`word_similarity`，阈值和 pool 固化在 retrieval version 中，仅以冻结中文集校准。[CITED: PostgreSQL pg_trgm docs] [ASSUMED: Chinese calibration risk]

### Pitfall 4: 版本切换与异步索引竞态
**What goes wrong:** 新 publication 已 active，但 vector 尚未生成；旧 vector 仍近邻靠前。  
**How to avoid:** exact/text 从 active pointer 立即读取；vector join 同一 current version，缺向量就是 text-only。新 model/dimension 只有全量完成并评测通过后切 active vector-space pointer。[VERIFIED: D-05/D-08/D-11]

### Pitfall 5: Graph State 兼容性被忽略
**What goes wrong:** 关系标签、候选 metadata 和 planning interrupt 会改变 checkpoint schema；旧 checkpoint resume 可能失败。  
**How to avoid:** 升级 meal/planning state version，提供旧版本 decode/default 或显式安全终止；对旧 checkpoint fixture 做 resume test。[VERIFIED: current versioned graph state]

### Pitfall 6: Langfuse “30 天”名义满足、实际永久保存
**What goes wrong:** OSS self-host 默认不会因一个环境变量自动清理；失败实验也可能被人为过滤。  
**How to avoid:** purge command 按 project/experiment allowlist 查询超过 30 天的成功与失败 traces，批量 DELETE，轮询回查；保留 purge report。测试 29/30/31 天边界和失败 trace。[CITED: Langfuse retention/deletion docs]

### Pitfall 7: admin manual retry 绕过审计或重复任务
**What goes wrong:** 页面直接改 job 状态或并发点击制造多个 provider 调用。  
**How to avoid:** 后端按 DB role 授权、append audit、idempotency key/unique constraint；仅允许 terminal failed 或 expired lease 的合法转移。[VERIFIED: existing admin RBAC/audit patterns]

### Pitfall 8: 可选观测反向污染发布结论
**What goes wrong:** Langfuse 上传失败让 evaluator 非零退出，或 dashboard 分数替换本地结果。  
**How to avoid:** evaluator 先原子写本地报告；publisher 是后置显式步骤并有独立 exit status。报告中的 PASS/FAIL 永不由上传响应改写。[VERIFIED: SPEC]

### Strict Embedding response DTO

```python
# Source: project AI-SPEC + Pydantic v2 contract
class EmbeddingBatch(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    model: str
    dimension: Literal[1024]
    vectors: list[list[float]]
    input_count: int = Field(ge=1, le=10)

    @model_validator(mode="after")
    def validate_shape(self):
        if len(self.vectors) != self.input_count:
            raise ValueError("embedding_count_mismatch")
        if any(len(v) != self.dimension for v in self.vectors):
            raise ValueError("embedding_dimension_mismatch")
        if any(not math.isfinite(x) for v in self.vectors for x in v):
            raise ValueError("embedding_non_finite")
        return self
```

## Open Questions

1. **关系层证据如何存储？**
   - What we know: 当前 catalog 只有 canonical/aliases/prepared_state/source，没有“地域/做法变体/同类”关系边。[VERIFIED: codebase]
   - What's unclear: 五个锁定例子中哪些由文本规则、受控 alias/relationship metadata 或 semantic-only 证明层级。
   - Recommendation: `0025` 增加版本化 controlled relation evidence（或版本化、可审计 rule table）；semantic-only 只能落最低层。由冻结集与目录管理员复核，不使用 LLM 动态分类。

2. **admin `catalog_version` 如何从常量迁移？**
   - What we know: 当前所有 admin publication 对外版本是 `admin-publication-v1`，但 UUID/content hash 不同。[VERIFIED: codebase]
   - What's unclear: 是否把 content hash 直接作为新版 catalog_version，还是引入稳定 display version + publication ID。
   - Recommendation: 在 Wave 0 写兼容测试后，选择不可变 content-derived version；历史 snapshot 按原值继续可读，新搜索只发新合同，绝不批量覆盖历史。

3. **Langfuse 30 天 purge 由谁触发？**
   - What we know: OSS 内置 retention 不可用，API 删除异步且需回查。[CITED: official docs]
   - What's unclear: 手动 Make/README 命令是否足够，还是本地 Compose 需要独立 cron 容器。
   - Recommendation: 提供确定性 `purge --older-than 30d --verify` 命令和测试；若 acceptance 要求自动执行，再加 Compose profile 下的独立 scheduler，不能接入业务 app lifespan。

4. **性能门槛尚未实测。**
   - What we know: AI-SPEC 建议 exact ≤50ms、text ≤150ms、hybrid ≤1.5s；当前目录规模和查询计划未基准。[VERIFIED: AI-SPEC + codebase]
   - Recommendation: 作为初始 budget 配置，不作为无证据发布声明；在真实 PostgreSQL fixture 上记录 p50/p95 和 `EXPLAIN (ANALYZE, BUFFERS)` 后冻结。
