## Summary

本次按标准深度逐文件审查了 Phase 06.3 的 Provider、混合检索、worker、控制面、Graph、评测、Langfuse、迁移和真实 E2E 路径。RBAC 的服务端复读、Activation 的 build/evidence 绑定、查询向量不落库以及前端安全投影总体方向正确；但当前 release gate 可以在资格过滤或降级语义失效时仍生成 `PASS`，并且 local 默认配置会让非精确检索直接 500。这两个问题必须在发布前修复。

## Critical Issues

### CR-01: 冻结评测没有断言资格排除、通道或执行模式

**File:** `backend/evals/phase_06_3/evaluate.py:381-390`  
**Issue:** 数据集显式冻结了 `excluded_food_ids`、`match_channel` 与 `execution_mode`，但 runner 只断言 action、目标集合和候选数量。`excluded_food_ids` 从未被读取；`match_channel`/`execution_mode` 也从未参与结果判定。更糟的是第 388 行把 `text_rows is not None` 和 `vector_rows is not None` 计为 SQL 覆盖——这两个 repository 方法始终返回 list，所以空结果也被计为已覆盖。于是失格、撤销、旧版本条目泄漏，或语义降级根本没有发生，仍可能产出 hash 有效的 `PASS` release，并被 activation 接受。

**Fix:** 为每个 case 记录并断言实际通道/降级状态；将 `excluded_food_ids` 映射到真实 publication UUID 并验证与 selected/candidate IDs 交集为空；按 `execution_mode` 注入并确认 timeout、缺索引、重复排序等故障条件。SQL 指标必须根据实际命中或受控查询计数采集，不能用 list 是否为 `None`。

### CR-02: local 默认 Fake embedding 会使所有非精确搜索失败为 500

**File:** `backend/app/core/config.py:86`  
**File:** `backend/app/providers/embedding/factory.py:28-43`  
**File:** `backend/app/nutrition/service.py:103-110`  
**Issue:** `Settings` 在 local 环境的默认 `embedding_provider_mode` 是 `fake`，factory 因此创建一个没有预置 outcome 的 `FakeEmbeddingProvider`。非精确搜索会调用它；Fake 会抛出 `ProviderCallError(PERMANENT, "FAKE_UNSCRIPTED_CALL")`，而 service 只把 transient/outcome-unknown 降级，永久错误会重新抛出。结果是默认本地应用中唯一精确匹配以外的查询无法走文本 `ASK` 降级，直接变成 500，违反本阶段“语义不可用时精确/文本继续工作”的安全降级合同。

**Fix:** local 默认改为显式 `disabled`，或将无脚本 Fake 的 `FAKE_UNSCRIPTED_CALL` 映射为安全的 text-only 降级；同时增加一个使用默认 `Settings(app_env="local")` 的端到端 service 测试，断言非精确查询返回 `ASK` 而不是异常。生产永久 Provider 拒绝仍应保留 fail-closed 行为。

## Warnings

### WR-01: 配置的周期成本上限从未被执行

**File:** `backend/app/providers/embedding/dashscope.py:40-60`  
**File:** `backend/app/providers/embedding/dashscope.py:173-175`  
**Issue:** `period_cap_cny` 被校验并保存到实例，但之后没有读取。实现只检查单次 cost，因此持续 worker 可无限累计 DashScope 费用，配置中的周期预算只是无效摆设。

**Fix:** 在持久化的、可跨进程原子协调的成本账本中按明确周期累计 embedding usage，并在发起 provider 调用前保留预算；达到 `period_cap_cny` 时返回稳定安全码、停止新调用且保留文本检索。

### WR-02: Langfuse 镜像拒绝所有失败 release，违反失败证据同等保留

**File:** `backend/evals/phase_06_3/langfuse_publish.py:81-85`  
**Issue:** Publisher 强制 `payload["decision"] == "PASS"`。因此带有效 hash 的 FAIL release 无法写入本地 Langfuse，和阶段决策 D-15“成功和失败实验都保留 30 天、不得隐藏失败来改变结论”冲突。虽然 case 内断言可出现 `FAIL`，整个评测失败时的证据仍被排除。

**Fix:** 允许结构、hash 与 allowlist 均有效的 `PASS` 和 `FAIL` release 被镜像；在 metadata 中安全投影 release decision，并确保 retention 对两者使用同一 trace-name/timestamp 选择条件。Activation 继续只接受 PASS release，不能把发布镜像权限当作 activation 权限。

### WR-03: 回滚迁移会删除数据库级 pg_trgm 扩展

**File:** `backend/migrations/versions/0025_hybrid_food_search.py:33`  
**File:** `backend/migrations/versions/0025_hybrid_food_search.py:223`  
**Issue:** upgrade 使用 `CREATE EXTENSION IF NOT EXISTS pg_trgm`，但 downgrade 无条件 `DROP EXTENSION IF EXISTS pg_trgm`。扩展是整个数据库共享对象；如果它在本迁移前就存在或被未审查模块使用，回滚会破坏无关索引/功能，或因依赖而让 rollback 失败。

**Fix:** 不在该 feature migration 的 downgrade 中删除共享 extension；将扩展视为数据库前置条件，或使用经部署治理记录的独立 extension migration 来管理其生命周期。
