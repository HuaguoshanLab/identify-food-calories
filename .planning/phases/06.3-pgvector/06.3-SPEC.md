# Phase 06.3: 混合菜品检索 — Specification

**Created:** 2026-09-10
**Ambiguity score:** 0.08 (gate: ≤ 0.20)
**Requirements:** 9 locked

## Goal

将当前仅依赖受控名称精确匹配的菜品搜索升级为精确名称、模糊文本与 pgvector 语义召回的受控混合检索，使餐食分析和饮食规划都能对非精确表达返回最多 3 个可确认候选，同时保证只有唯一精确匹配可以自动选中。

## Background

当前 `NutritionService.search_food_catalog` 会规范化查询，并通过 `NutritionRepository.search_qualified_foods` 查询受控目录；唯一精确别名可直接通过，其余情况要求用户选择。实际 PostgreSQL adapter 先使用 `contains`，随后又在 Python 中只保留与 alias 完全相等的名称，因此“西红柿炒鸡蛋”“风干牛肉”“四川烤鱼”等相关表达不能稳定召回受控候选。

项目已有 pgvector 扩展和 embedding metadata 表，但现有列为测试性质的 `vector(3)`，检索查询仍使用 `ILIKE`，尚无真实查询向量、向量距离排序或混合融合。餐食分析和饮食规划均依赖同一确定性 Nutrition Tool 边界，因此本阶段必须升级该边界而不能让模型直接决定营养条目。

项目已有 Git 冻结评测、代码评测、Promptfoo 和 Phoenix 观测体系。本阶段新增本地 Docker 自托管 Langfuse，用于保存去标识化的 Dataset Experiment、逐例 Score 和版本对比；它不取代 Git 冻结数据集、本地确定性门禁、Promptfoo 或 Phoenix。

## Requirements

1. **唯一精确匹配优先**：唯一受控 canonical name 或 alias 精确匹配必须直接选择对应菜品，且不得被模糊或语义候选覆盖。
   - Current: 唯一精确 alias 可以通过，但 imported catalog 与 admin publication 的匹配路径不统一，且搜索接口不显式区分匹配通道。
   - Target: 餐食分析和饮食规划共享同一精确优先规则；查询“米饭”存在唯一精确条目时直接选择米饭，不返回“蛋炒饭”要求确认。
   - Acceptance: 冻结用例中“米饭”在存在唯一受控精确条目时返回 `PASS` 且 selected food 为米饭；改变模糊或向量排名不得改变该结果。

2. **非精确混合召回**：没有唯一精确匹配时，系统必须综合模糊文本与 pgvector 语义召回，去重后返回最多 3 个当前有效的受控候选。
   - Current: 非精确查询最终被 Python exact-membership 过滤，pgvector embedding 未参与菜品解析。
   - Target: 相关名称、地域修饰、同义表达和近义菜品可进入 Top 3；同一菜品被多个通道召回时只出现一次，排序可重复。
   - Acceptance: 固定数据库快照、查询和检索版本下重复运行产生完全一致的候选 ID 顺序，候选数为 0–3 且无重复 ID。

3. **非精确结果强制确认**：所有仅由模糊文本或语义通道召回的结果都必须返回 `ASK`，不允许根据相似度或排名自动选中。
   - Current: 当前没有真实非精确召回，因此尚无跨通道的强制确认合同。
   - Target: 即使只有一个高相关非精确候选，餐食分析和饮食规划也必须要求用户确认。
   - Acceptance: 所有标记 `auto_pass_allowed=false` 的冻结用例均返回 `ASK`；非精确自动选择计数为 0。

4. **两个 Agent 流程一致覆盖**：混合检索必须同时用于餐食分析和饮食规划，不得形成两套不同的菜品解析规则。
   - Current: 两个图通过 Nutrition/Planning Tool adapter 使用受控目录，但尚未具备共享混合检索合同。
   - Target: 两个流程通过同一受控搜索能力获得相同查询的相同候选集合和选择语义。
   - Acceptance: 对同一目录快照和同一查询，餐食分析与饮食规划的工具级测试得到相同候选 ID 顺序、相同 `PASS/ASK` 决策。

5. **目录资格与版本隔离**：召回只能包含当前可计算、未撤销、未失格、版本明确的目录条目；搜索命中不能绕过最终权威读取。
   - Current: 精确搜索已有 qualified/version/publication eligibility 条件，但新的模糊和向量通道尚不存在。
   - Target: 每个召回通道均在结果物化前执行相同资格边界；用户确认后仍按 `food_id + catalog_version` 从权威目录重新读取并确定性计算。
   - Acceptance: 包含失格、撤销、旧版本和缺失营养字段条目的数据库用例中，这些条目均不出现在候选中，泄露计数为 0。

6. **安全降级**：语义检索不可用、超时或索引缺失时，精确与模糊文本搜索必须继续工作，且不得扩大自动选择权限。
   - Current: 没有菜品语义调用和对应降级合同。
   - Target: 向量能力失败被映射为安全、可观测的降级状态；唯一精确结果仍可 `PASS`，其余文本候选仍为 `ASK`。
   - Acceptance: Fake Embedding Provider 失败和 PostgreSQL 向量查询失败测试均不会导致唯一精确用例失败，也不会导致任何非精确候选自动选中。

7. **冻结检索评测集**：仓库必须保存版本化、去标识化、带内容 hash 的检索数据集，覆盖精确、相关表达、歧义、无结果、资格过滤和降级。
   - Current: 已有其他阶段的冻结评测资产，但没有 Phase 06.3 菜品混合检索数据集。
   - Target: 数据集至少包含“西红柿炒鸡蛋→番茄炒蛋”“风干牛肉→牛肉干”“四川烤鱼→烤鱼”“定西土豆粉→土豆粉”“包子→生煎包”等 Top 3 非精确用例；这些 fixture 中不得同时存在会触发唯一精确优先的同名受控条目。
   - Acceptance: 数据集 schema 和 hash 校验通过；每个非精确用例的期望目标进入 Top 3、返回 `ASK`，不要求目标排名第一。

8. **本地 Langfuse 实验记录**：项目必须提供可选的本地 Docker 自托管 Langfuse 评测路径，用于展示同一冻结数据集上的 Experiment、逐例代码评分和版本对比。
   - Current: 项目使用 Phoenix 和本地评测资产，没有 Langfuse 运行配置或实验记录路径。
   - Target: 开发者可以显式启动隔离的 Langfuse 服务，并将 dataset hash、代码版本、检索版本、embedding model/version、候选安全投影、耗时和确定性评分写入一次 Experiment。
   - Acceptance: 在本地 Langfuse 中可查看一轮完整实验及 `exact_match_precision`、`non_exact_auto_select_count`、`top3_recall`、`ineligible_leak_count`、`fallback_success` 和 `deterministic_order` 评分；Langfuse 数据库与业务 PostgreSQL 不共库。

9. **验收独立与数据最小化**：最终 PASS/FAIL 必须由仓库内确定性评测产生，Langfuse 仅保存可选镜像证据且不得接收敏感数据。
   - Current: 项目已有独立发布证据和最小化 tracing 原则，但本阶段尚未定义 Langfuse 边界。
   - Target: Langfuse 离线或未配置时，本地和 CI 仍能完成全部检索验收；不得发送真实用户餐食、用户标识、身体数据、图片、完整提示词、Provider 原文、密钥或思维链。
   - Acceptance: 禁用 Langfuse 后同一冻结数据集仍生成相同 PASS/FAIL 报告；安全测试确认导出的字段仅来自显式 allowlist，且报告绑定 dataset hash、代码版本和检索版本。

## Boundaries

**In scope:**
- 受控菜品 canonical name 与 alias 的唯一精确优先行为。
- 无唯一精确结果时的模糊文本和 pgvector 语义召回。
- 多通道去重、确定性排序和最多 3 个候选。
- 所有非精确候选强制用户确认。
- 餐食分析与饮食规划共享同一搜索语义。
- 当前目录资格、publication eligibility 和版本隔离。
- 语义检索失败时的精确/文本降级。
- Phase 06.3 冻结检索数据集、确定性评测与发布报告。
- 隔离的本地 Docker Langfuse Dataset Experiment 和安全评分镜像。

**Out of scope:**
- 非精确候选自动选择 — 误选会让后续正确计算建立在错误食物上。
- 修改营养计算、份量换算或异常校验规则 — 本阶段只改变候选召回。
- 让 LLM、reranker 或联网搜索生成营养数值或决定权威条目 — 数值真相继续来自 PostgreSQL 受控目录。
- Elasticsearch、RabbitMQ、MongoDB 或 Neo4j — 当前 PostgreSQL、pgvector 和既有 worker 足以承载本阶段。
- 从真实用户输入自动学习新 alias — 未审核输入不能污染全局目录。
- 前端页面重设计 — 复用现有追问与候选确认交互。
- 替换 Phoenix 或 Promptfoo — Langfuse 只补充本阶段的本地 Dataset Experiment 能力。
- 生产高可用 Langfuse 部署 — 本阶段只交付本地 Docker、自托管评测路径。

## Constraints

- PostgreSQL 继续是营养目录和资格状态的唯一权威来源；任何搜索索引只能是可重建派生数据。
- Agent 图只能通过现有窄 Tool/Service 边界使用检索，不得直接访问 Repository、SQLAlchemy、embedding SDK 或 Langfuse。
- Embedding 能力必须遵循项目 Provider/DTO/Factory/Fake 分离规则，并执行维度、数量、有限数值、超时、重试和成本校验。
- API Schema、Provider DTO、Graph State、ORM Model 和内部搜索命中 DTO 必须分离。
- 非精确召回阈值和排序规则必须版本化并由冻结数据校准，不能凭主观值宣称通过。
- 新 schema 必须通过保持单一 head 的 Alembic migration 交付。
- Langfuse 必须独立存储、默认可关闭；未配置时不得阻止应用启动或本地/CI 确定性验收。
- Langfuse 只接受合成或去标识化数据及 allowlist metadata；原始图片和健康数据不得进入其 traces、datasets 或 media。

## Acceptance Criteria

- [ ] 唯一精确查询“米饭”直接选择米饭，且不被“蛋炒饭”等相关候选覆盖。
- [ ] 非精确查询最多返回 3 个无重复、当前有效、版本明确的受控候选。
- [ ] 所有仅由模糊或语义通道命中的用例返回 `ASK`，非精确自动选中次数为 0。
- [ ] 五个锁定相关表达的预期条目均进入 Top 3，且测试 fixture 不用精确同名条目绕过语义召回。
- [ ] 餐食分析与饮食规划对同一查询产生相同候选顺序和选择动作。
- [ ] 失格、撤销、旧版本和不可计算条目候选泄露数为 0。
- [ ] 语义服务或向量查询失败时，精确和文本搜索仍可用且安全规则不降级。
- [ ] 相同数据、查询和版本重复执行时候选顺序完全一致。
- [ ] Git 冻结数据集通过 schema/hash 校验，发布报告绑定 dataset、代码、检索和 embedding 版本。
- [ ] 本地 Docker Langfuse 可查看完整 Experiment 和六项锁定评分，且不与业务 PostgreSQL 共库。
- [ ] 禁用或断开 Langfuse 后，本地/CI 仍生成相同的确定性 PASS/FAIL 报告。
- [ ] Langfuse 输出字段 allowlist 测试证明没有真实用户身份、餐食、身体数据、图片、完整提示词、Provider 原文、密钥或思维链。
