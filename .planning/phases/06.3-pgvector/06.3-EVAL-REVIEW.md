## Critical Gaps

- **BLOCKER — 关系边界与用户可解释性缺失。** 计划规定了三种允许关系标签和关系层排序，但生产的 `FoodSearchResult`/Graph candidate 投影没有保留这些关系。评测器不得不用固定 `目录候选` 伪标签，因此无法证明也实际未交付所承诺的用户可解释性。按 AI-SPEC 的维度，这是 MISSING，不是“有一些融合器单测”就能降级为 PARTIAL。

## Remediation Plan

### Must fix before production:

1. 让公开/Graph 使用的 search result 保留 `FoodSearchCandidate` 的 allowlisted `relation`、prepared state、portion hints 与 source name；不得重新只投影成 `QualifiedFood`。同步限制 relation 为三项枚举，禁止 score/rank/vector 泄漏。
2. 扩展 `evaluate.py` 和 release schema：每个非精确 case 断言候选 relation、层级顺序、去重和“不以共享食材补位”；将这些 assertions 计入 PASS hard gate。添加负向用例，证明泛化 `目录候选`、跨层排序和无关补位都会 FAIL。
3. 在 dataset 变更流程加入可审计的版本化审核 artifact：目录管理员 + 营养师 + 中文菜系专家审核新增/修改的 relation labels 与排除项。没有签核不得替换冻结标签。

### Should fix soon:

1. 在 release 中记录 exact、text fallback、hybrid 的实际安全终态时长，按 AI-SPEC 的 50ms / 150ms / 1.5s 初始 SLO 评分；缺失或超阈值应明确 FAIL/WARN，而非只写 latency bucket。
2. 在 Phoenix allowlist 拒绝时发出 payload-free `error.code` 与可路由计数；实现并告警语义降级率、零候选率、确认后失效、索引滞后、预算/任务耗尽和用户改选/取消的聚合指标。
3. 使用本地 Langfuse 对合成 frozen experiment 至少做一次 publish + 30 天 purge/requery 演练，保存不含 payload 的验证记录；由隐私/安全负责人审核字段 allowlist 与保留策略。

### Nice to have:

1. 建立 nightly frozen-suite 和不可覆盖的失败历史归档；生产信号只能转写为人工构造的合成案例。
2. 为相近地域菜式、共享食材负例和候选不足 3 条添加更多已审核案例，以扩大关系层回归覆盖面。
