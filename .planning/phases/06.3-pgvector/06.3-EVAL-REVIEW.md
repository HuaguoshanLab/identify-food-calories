## Critical Gaps

- **BLOCKER — flow semantics parity 未实现。** 评测器没有比较餐食分析与饮食规划的真实检索输出，也没有计算或门禁 `flow_semantics_parity == 1.0`。这直接遗漏 AI-SPEC 的 Critical 维度。
- **BLOCKER — CI/CD 没有执行冻结门禁。** 当前 release evidence 能由本地人工命令生成/验证，但仓库中没有把 evaluator、真实 PG 集成测试和 release verification 变成合并/发布的自动阻断条件。

## Remediation Plan

### Must fix before production:

1. 扩展 `evaluate.py` 的每案 evidence：从两个生产 Tool/Graph 入口捕获并比较 `action`、`selected_food_id`、候选 `(food_id, catalog_version)` 有序列表及 relation labels；新增 `flow_semantics_parity` 到 release metrics，分母为 24，任何不一致、零分母或缺字段必须使 decision 为 FAIL。添加针对“计数相同但输出不同”的负向合同测试。
2. 新增仓库 CI workflow（或已存在的等效 pipeline 配置），在 PostgreSQL/pgvector 服务下依次运行 Phase 06.3 unit、真实 PG retrieval/integration、fresh evaluator 及 `--verify-release`。将 evaluator 的非零退出、缺 hash、FAIL report 和零分母设为不可绕过的合并/发布失败。

### Should fix soon:

1. 在 release evidence 中增加关系标签/层级的逐案断言；保存由目录管理员和中文菜系专家审核新增/修改冻结案例的版本化签核记录。
2. 记录每案/每通道的安全终态耗时，按 AI-SPEC SLO 对 exact/text fallback/hybrid 评分；超时或缺失测量即 FAIL。
3. 让 tracing allowlist 拒绝产生 payload-free `error.code`/计数和可路由告警，而不只是静默 drop；实现语义降级、零候选、确认失效、索引滞后和用户改选/取消的聚合监测与阈值告警。
4. 用本地 Docker Langfuse 做一次合成冻结 Experiment 的发布与 30 天 purge 演练，保存不含 payload 的删除 verification 证据，并取得隐私/安全负责人对字段 allowlist 的签核。

### Nice to have:

1. 为冻结集建立定期夜间全量运行和失败历史归档；新生产故障只能以人工构造的合成等价案例进入数据集。
2. 为关系层负例、索引滞后和用户确认后改选增加版本化的趋势摘要，便于人工月度复核。
