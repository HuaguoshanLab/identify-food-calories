# Phase 06.3: 混合菜品检索 - Context

**Gathered:** 2026-09-10
**Status:** Ready for planning

<domain>
## Phase Boundary

本阶段把受控菜品目录的解析能力升级为“唯一精确匹配优先，非精确时由模糊文本与 pgvector 共同召回”的混合检索，并让餐食分析和饮食规划共享同一套搜索与确认语义。

本阶段只改变候选召回、资格过滤、索引生命周期和检索评测，不改变营养计算、份量换算、异常校验或现有前端交互模型。PostgreSQL 仍是权威目录，搜索索引只是可重建的派生数据。
</domain>

<spec_lock>
## Requirements (locked via SPEC.md)

**9 requirements are locked.** See `06.3-SPEC.md` for the complete requirement statements and acceptance criteria. Discussion may refine implementation but must not weaken these requirements.

### In scope

- 受控菜品 canonical name 与 alias 的唯一精确优先行为。
- 无唯一精确结果时的模糊文本和 pgvector 语义召回。
- 多通道去重、确定性排序和最多 3 个候选。
- 所有非精确候选强制用户确认。
- 餐食分析与饮食规划共享同一搜索语义。
- 当前目录资格、publication eligibility 和版本隔离。
- 语义检索失败时的精确/文本降级。
- Phase 06.3 冻结检索数据集、确定性评测与发布报告。
- 隔离的本地 Docker Langfuse Dataset Experiment 和安全评分镜像。

### Out of scope

- 非精确候选自动选择。
- 修改营养计算、份量换算或异常校验规则。
- 让 LLM、reranker 或联网搜索生成营养数值或决定权威条目。
- 引入 Elasticsearch、RabbitMQ、MongoDB 或 Neo4j。
- 从真实用户输入自动学习新 alias。
- 前端页面重设计。
- 用 Langfuse 替换 Phoenix 或 Promptfoo。
- 生产高可用 Langfuse 部署。
</spec_lock>

<decisions>
## Implementation Decisions

### 相关候选边界

- **D-01 受控相关范围：** 非精确召回允许同义名、地域修饰、相近做法和同类成品菜；不得仅因共享一个食材就召回完全不同的菜品。
- **D-02 分层排序：** 候选关系按“同一道菜的名称变体 → 地域/做法变体 → 同类成品菜”分层；向量相似度只能在同一关系层内参与排序，不能越层压过更直接的关系。
- **D-03 不凑满 Top 3：** 可靠候选不足 3 个时有几个返回几个；低质量候选不得为了填满列表进入结果。
- **D-04 用户可理解的原因：** 候选显示简短关系标签，例如“名称相近”“地域/做法变体”“同类食物”，并复用现有做法、份量或来源信息；不得向用户暴露内部相似度分数。

### 目录发布后的生效方式

- **D-05 分阶段生效：** 新菜发布后，精确名称和模糊文本检索立即生效，语义索引异步补齐。
- **D-06 索引失败不回滚发布：** Embedding 生成失败不回滚已经有效的目录发布；系统执行有限自动重试，在后台显示索引状态，并允许管理员手动重试。
- **D-07 资格实时生效：** 菜品失格或撤销后，所有召回通道必须通过 PostgreSQL 当前资格条件立即排除它；派生向量和索引记录可稍后物理清理。
- **D-08 版本原子切换：** 新目录版本发布后，精确和文本搜索原子切换到新版本，旧版本立即退出新的搜索结果；已有历史快照保持不变，新版本语义索引异步补齐。

### Embedding 运行方式

- **D-09 Provider 边界：** Embedding 使用可替换 Provider，生产默认 DashScope，测试只使用 Fake Provider；Agent 图不得直接调用 Embedding SDK。
- **D-10 最小化输入：** 只向 Embedding Provider 发送规范化后的单项菜名，不发送完整餐食描述、份量、用户身份、身体数据或健康数据。
- **D-11 向量空间升级：** 模型或维度升级时并行构建新索引；新索引完整且冻结评测通过后才能原子切换。不同模型或维度的向量严禁混合检索。
- **D-12 不持久化用户查询向量：** 用户查询文本和查询向量不得持久化，最多在当前 Agent 运行内复用；数据库只保存受控目录条目的向量。

### Langfuse 运行与保留策略

- **D-13 显式启动：** Langfuse 只在显式运行混合检索实验时通过独立 Docker Compose 启动。应用日常启动、普通测试和 CI 确定性门禁均不得依赖 Langfuse。
- **D-14 保留 30 天：** Langfuse 中逐例 Trace 和 Score 保留 30 天；Git 永久保存冻结数据集、汇总报告及其 dataset、代码、检索和 embedding 版本 hash。
- **D-15 失败记录同等保留：** 成功和失败实验都保留 30 天，不隐藏或删除失败结果来改变结论；发布报告必须如实保留 FAIL。
- **D-16 显式发布：** 本地评测默认只生成本地报告，只有传入明确参数（例如 `--publish-langfuse`）才写入 Langfuse；发布前必须通过字段 allowlist 校验。

### the agent's Discretion

- PostgreSQL 模糊文本实现、阈值和索引选择，例如 `pg_trgm`、归一化策略及其阈值；最终参数必须由冻结数据集校准。
- 文本和向量通道的候选池大小、融合公式、稳定 tie-breaker 和关系层判定实现，但必须满足 D-01 至 D-04 及确定性顺序要求。
- 派生向量表、索引状态表、任务租约、outbox、重试次数和退避参数的具体 schema 与机制；必须保持 Alembic 单一 head。
- DashScope 的具体 embedding 模型、向量维度、超时与成本上限；必须有明确版本标识并能使用 Fake Provider 完成测试。
- Langfuse 独立 Compose 的具体服务拓扑、保留策略执行方式、实验命名和安全投影字段；不得与业务 PostgreSQL 共库或突破数据最小化边界。
- 后台索引状态和手动重试复用现有管理能力的具体 API/页面落点；不进行前端重设计。
</decisions>

## Existing Code Insights

### Reusable Assets

- `backend/app/nutrition/service.py` — 当前确定性菜品选择与 `PASS/ASK` 决策层，应成为混合召回结果进入业务语义的唯一入口。
- `backend/app/nutrition/repository.py` — 当前精确 alias、qualified food 和 publication eligibility 查询，可扩展为统一资格过滤的检索端口。
- `backend/app/agent/tools.py` — 餐食分析与饮食规划共用的工具边界；两个图应通过这里共享检索语义。
- `backend/app/providers/reasoning/` 与 `backend/app/providers/vision/` — Provider、DTO、Factory、Fake 的既有模式，可用于新增 Embedding Provider。
- `backend/app/core/tracing.py` — 现有 Phoenix allowlist 和数据最小化模式，可用于约束 Langfuse 安全投影。
- `backend/evals/` — 冻结数据集、hash、确定性评测和发布证据的既有模式。

### Established Patterns

- 后端依赖方向保持 API → Application/Service → Repository → Model。
- LangGraph 只能调用工具，不能直接访问数据库、Provider SDK 或 Langfuse。
- 唯一受控精确匹配可 `PASS`；所有非精确召回必须 `ASK`。
- 数据库迁移维持单一 Alembic head，派生索引可重建，PostgreSQL 业务目录始终权威。
- Provider 的生产实现与 Fake 实现分离，测试不得调用真实外部模型。

### Integration Points

- 扩展 nutrition repository port、service 和 PostgreSQL adapter，输出带匹配通道、关系层和版本信息的内部候选 DTO。
- 新增 Embedding Provider/DTO/Factory/Fake，并由应用服务而非 Agent 图或 Repository 直接编排外部调用。
- 通过 migration 增加真实维度的目录向量、索引版本和异步状态；接入既有发布、撤销、失格与版本切换流程。
- 让餐食分析和饮食规划的 tool adapter 调用同一搜索服务，保持相同候选顺序和 `PASS/ASK` 结果。
- 扩展后台目录索引状态与手动重试能力，同时保持现有 RBAC 和审计日志。
- 在 `backend/evals/` 增加 Phase 06.3 冻结数据集、确定性 runner、发布报告，以及可选 Langfuse 镜像发布器。

<specifics>
## Specific Ideas

- 2026-09-12 用户确认：当前真实目录没有“番茄炒蛋”和“西红柿炒鸡蛋”。撤销这组菜名的真实检索及计划替换验收，不再将未召回视为检索缺陷，也不要求为此新增菜谱。下列冻结用例使用自建合成目录，仅验证机制，不代表真实目录覆盖。
- 唯一精确输入“米饭”必须直接选择米饭，不能被“蛋炒饭”覆盖或要求确认。
- 非精确冻结用例至少包含：西红柿炒鸡蛋 → 番茄炒蛋、风干牛肉 → 牛肉干、四川烤鱼 → 烤鱼、定西土豆粉 → 土豆粉、包子 → 生煎包。
- 上述非精确目标只要求进入 Top 3，不要求排第一，也绝不允许自动选中。
- 候选关系标签使用用户可理解的短语，例如“名称相近”“地域/做法变体”“同类食物”，不显示向量距离或融合分数。
- Langfuse 记录去标识化的 dataset hash、代码版本、检索版本、embedding model/version、候选安全投影、耗时及六项锁定评分；不记录真实用户输入、图片、完整提示词、Provider 原文或思维链。
</specifics>
