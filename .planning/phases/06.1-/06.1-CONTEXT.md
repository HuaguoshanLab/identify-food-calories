# Phase 06.1: 菜谱管理与餐单候选池 - Context

**Gathered:** 2026-09-07
**Status:** Ready for planning

<domain>
## Phase Boundary

本阶段在独立后台增加与“营养目录”同级的“菜谱管理”，将管理员导入并维护的成品菜餐单候选接入用户端 `/app/plans`。它解决“计划页总是同几道菜”的实际问题：新计划只能从已启用、营养目录合格的候选池中选择，并避开固定地拿排序第一条。

范围包括：候选菜谱的单条维护、CSV 模板/预览/导入/导出、批量启用/停用/软删除、管理员审计、成品菜与营养目录的关联校验、以及规划领域对可选加餐的支持。

范围不包括完整食谱配方、食材级配方编辑、烹饪步骤、购物清单或医疗建议；这些不能伪装成“菜谱管理”的一部分塞进本阶段。

</domain>

<decisions>
## Implementation Decisions

### 成品菜候选的业务模型

- **D-01：** 当前导入的“辣椒炒肉”等成品菜按**单品菜谱候选**处理，不要求也不虚构食材配方。每条候选关联一条已发布且合格的营养目录成品菜，使用该条目的每 100g 营养和候选中填写的份量克数作确定性计算。
- **D-02：** 候选的管理员可见字段至少为：关联目录菜品名称、餐次、单份克数、份量说明、做法标签、口味标签、状态。餐次固定为早餐、午餐、晚餐、加餐；做法和口味使用受控下拉选项，避免自由文本造成无法筛选和不一致。
- **D-03：** 导入候选时，“关联目录菜品名称”必须能唯一匹配已发布的营养目录条目；缺失、歧义、停用或营养不合格均在预览阶段按行报错，不能自动创建营养目录条目，也不能猜测关联关系。
- **D-04：** 复杂的“多个食材组成一个食谱”保留为后续独立能力。它需要配方版本、食材损耗与营养汇总规则，不能用现有成品菜能量数据假装已经具备。

### 后台操作与数据生命周期

- **D-05：** 在后台主导航中，`菜谱管理` 紧跟 `营养目录`，与概览、运行审计、模型配置、操作审计同级；用户 H5 不增加后台入口。“餐单生成”仍是用户端计划页的能力，不单独成为后台导航页。
- **D-06：** 菜谱管理采用现有营养目录的表格、筛选、分页、导入预览与确认交互模式，保持“快速、能操作”的后台，而不是另做复杂食谱编辑器。
- **D-07：** CSV 导入先预览，只有所有行合法时才能确认导入；一次导入有大小和行数上限，并提供清晰的行号/字段错误。确认导入、批量状态变更均要求原因、幂等键、管理员实时 RBAC 与审计记录；任一行失败时整批回滚。
- **D-08：** 候选状态至少包含`待审核`、`已启用`、`已停用`与软删除状态。只有`已启用`的候选可参与后续餐单；停用和删除立即阻断新计划，但绝不改写已经生成或保存的历史营养快照。
- **D-09：** 批量删除是可恢复的软删除，默认列表不显示已删除项但可审计和查询；不得物理删除仍被历史计划引用的证据。批量启用、停用、删除只作用于当前筛选页中显式勾选的项目，并在确认对话框中显示数量和原因。
- **D-10：** 导入、导出、批量启用、批量停用和批量删除均是本阶段正式能力。导出遵从当前筛选条件，下载可再次导入的 UTF-8 BOM CSV，并对可能触发 Excel 公式执行的字段作安全转义。

### 餐单生成与可选加餐

- **D-11：** 计划生成的三个主餐仍是必需槽位；不再按数据库排序固定选每餐第一道候选。合格候选池要以可审计、可复现的轮换/近期使用规避策略参与组合，使连续生成在满足忌口、口味、营养目标和重复度约束时能够切换候选。
- **D-12：** 用户明确选择：**加餐按需生成，不固定出现。** 只有存在已启用的加餐候选、并且加入后仍能通过当天总能量/宏量和重复度校验时，计划才展示加餐卡片；没有合适加餐时正常交付三餐，不能为了凑四餐硬塞一道菜。
- **D-13：** 加餐是规划领域的正式槽位：数据库约束、运行时 Schema、组合逻辑、营养校验、计划归档、反馈替换和用户端展示必须一致支持它。任何一个环节仍只认三餐，都会把“按需加餐”做成假功能。
- **D-14：** 每次计划保留当次候选、份量、目录/候选版本与确定性计算结果的稳定快照。之后停用、删除或更新候选只影响未来计划，不能回写既有计划。

### the agent's Discretion

- 在不突破上述行为的前提下，确定候选稳定 ID、版本字段、关系表、迁移拆分、查询索引、轮换种子和近期使用窗口。
- 复用现有目录导入的安全限制；依据候选 CSV 的实际列宽和现有 500 行批量边界确定模板与拆分提示。
- 选择最小、可访问的后台筛选项与用户端“加餐为可选”的展示文案，不新增用户端 Tab 或独立计划入口。

</decisions>

## Existing Code Insights

### Reusable Assets

- `backend/app/admin/catalog_csv.py`：已有 UTF-8 CSV、错误行号、全量校验、500 行/1MB 限制以及防 Excel 公式执行的导出处理；菜谱 CSV 应沿用，不复制一份脆弱解析器。
- `backend/app/admin/service.py` 与 `repository.py`：已有实时管理员角色确认、原因、幂等账本、advisory lock、事务回滚和字段级审计模式。
- `admin-frontend/src/features/catalog/`：已有表格、当前页选择、导入预览、导出、分页、确认对话框和状态反馈；新功能可以复制结构，不共享私有领域 DTO。
- `backend/app/planning/`：已有候选资质过滤、食材营养确定性重算、日目标校验、计划归档和反馈替换能力。
- `frontend/src/features/records/api/mealMetadata.ts` 与记录/看板后端：已经稳定支持 `snack`，可作为用户侧餐次命名和展示的一致来源。

### Established Patterns

- API 只做 HTTP 翻译；应用服务掌握事务与业务规则；Repository 只持久化；数据库变更必须以 Alembic 交付。
- 目录条目、候选、计划与历史记录都必须保留版本/快照证据；模型不能生成或覆盖营养数值。
- 后台每个端点在 Service 内重新读取数据库角色，前端导航和按钮隐藏不是授权。
- CSV 预览不写库；确认导入必须使用同一内容、原因和幂等键；全批成功才提交。
- 用户可见页面需要组件测试、真实 PostgreSQL/API 测试、Playwright 与内置浏览器实际路径验收。

### Integration Points

- 在 `admin-frontend/src/layouts/AdminShell.tsx` 添加 `/admin/recipes`，并在 `admin-frontend/src/features/` 建立独立 recipe feature。
- 在 `backend/app/admin/` 新增受 RBAC 和审计保护的菜谱候选 API，或在保持分层的前提下抽取共享的后台基础设施；不得让前端或 Graph 直接写规划表。
- 规划 Service/Repository 要将“可选加餐”与“候选轮换”放在同一受控组合路径，Graph 继续只调用窄工具接口。
- 对 `controlled_recipes` 的餐次检查、枚举、导入器、归档 DTO 和测试做同次迁移，避免 API 支持加餐而数据库拒绝。
- 历史计划、已确认餐食和其营养快照继续只读，不受管理候选状态变化影响。

</code_context>

<specifics>
## Specific Ideas

- 用户已整理并填写 612 条成品菜餐单候选；餐次分布为早餐、午餐、晚餐和加餐，状态为待审核。
- 用户偏好快速、表格化后台：关联目录菜品、餐次、单份克数、份量说明、做法标签、口味标签、状态均应能直接看懂和操作。
- 用户明确指出：营养目录与菜谱管理是不同层级；计划页必须真正使用已启用候选，不接受只增加菜单或固定演示菜。

</specifics>

<deferred>
## Deferred Ideas

- 多食材配方、食材替换、烹饪损耗、步骤和购物清单 — 需要独立的配方领域和数据输入，不属于当前成品菜候选池。
- 将候选使用频率做成长周期个性化推荐 — 当前阶段只实现受控轮换/近期规避与可追溯选择，不构建推荐系统。

</deferred>
