# Phase 06.1: 菜谱管理与餐单候选池 - Research

**Researched:** 2026-09-07
**Domain:** 受控成品菜候选、后台批量治理、可复现餐单组合与按需加餐
**Confidence:** HIGH（以当前代码和已锁定阶段合同为准；不新增第三方依赖）

<user_constraints>
## 已锁定的产品约束

- 成品菜是单品菜谱候选：关联营养目录成品菜，以目录每 100g 营养 × 固定份量作确定性计算；不虚构食材配方。
- `菜谱管理` 是独立后台一级导航；需提供 CSV 导入、导出、批量启用、停用、软删除。
- 只有已启用且关联目录仍合格的候选可以进入后续计划；历史计划/餐食快照绝不回写。
- 三个主餐必须生成；加餐由用户明确选择为按需生成，只有加入后仍通过整日校验才显示。
- 计划不能再固定选择每个槽位排序第一条候选；选择过程必须可审计、可复现且避免近期重复。

来源：`.planning/phases/06.1-/06.1-CONTEXT.md`。

</user_constraints>

<codebase_findings>
## 已确认的代码事实

### 1. 重复菜的根因已定位

`PlanningService.compose_daily_meals()` 在遍历 `MealSlot` 时用 `next(...)` 选取第一条符合条件的候选；`SqlAlchemyPlanningProfileRepository.list_controlled_recipes()` 又按 `meal_slot, display_name` 排序。因此相同输入必然稳定命中同几条菜，并非随机问题。

当前查询还强制：`is_active`、`source_kind == project_authored`、项目内部许可证、审核人角色、固定 `recipe_version`、固定 `catalog_version`，并检查每个 ingredient 的目录资格。这解释了为什么后台新增营养目录条目不会自动进入计划。

来源：`backend/app/planning/service.py`、`backend/app/planning/repository.py`、`backend/app/agent/tools.py`。

### 2. 当前受控菜谱模型不能直接接收管理员成品菜

`controlled_recipes` 当前限制：

- `meal_slot IN ('breakfast', 'lunch', 'dinner')`；
- `source_kind = 'project_authored'`；
- 固定项目许可证、审核状态和审核角色；
- 每条菜谱至少有一个 `controlled_recipe_ingredients` 食材关联；
- `recipe_version = controlled-recipes.v2` 由 Agent 工具硬编码传入。

管理员管理的单品成品菜不能把这些约束改松后直接塞进去，否则会混淆“项目自有多食材 seed”和“管理员维护的成品菜候选”两种证据模型。推荐新增一个明确的管理员候选记录/版本边界，引用合格的 `FoodCatalogItem`，并保持旧 seed 可审计但不再是唯一生产候选来源。

来源：`backend/app/planning/models.py`、`backend/app/planning/schemas.py`、`backend/app/planning/importer.py`、`backend/app/agent/tools.py`。

### 3. 加餐联动点是完整链路，不是一个枚举

当前以下位置都将计划锁定为三餐：

- `MealSlot` 只有早餐、午餐、晚餐；`PlanValidationResult`、组合和去重逻辑遍历全部槽位。
- 数据库检查约束拒绝 `snack`。
- JSON seed importer 要求槽位集合恰好为三餐。
- `PlanReport.meals`、`PlanArchiveWrite.recipe_ids` 均要求恰好三项，归档还要求槽位次序等于全部 `MealSlot`。
- 规划图调整路径要求 `len(current.meals) == 3`，缺少槽位选择时只提供三餐；`_slot_from_feedback()` 也不识别加餐。
- 用户端 `MealCard.tsx` 的标签映射只包含三餐。

而“餐食记录”和看板已经稳定支持 `snack`。因此规划领域应以“固定三主餐 + 可选第四张加餐”的不变量表达，而不能把 `snack` 简单加入现有 `MealSlot` 后仍让所有 `len(MealSlot)` 规则把它当成强制槽位。

来源：`backend/app/planning/schemas.py`、`models.py`、`archive_schemas.py`、`archive_service.py`、`importer.py`、`backend/app/agent/graph.py`、`frontend/src/features/plans/components/MealCard.tsx`、`frontend/src/features/records/api/mealMetadata.ts`。

### 4. 后台 CSV 与批量操作已有可复用的安全基线

营养目录已有完整实现：UTF-8 BOM CSV、精确中文表头、1MB/500 行限制、逐行预览错误、全量通过后才确认、一次导入事务、管理员绑定的幂等键/advisory lock、原因审计、导出防 Excel 公式执行。后台 UI 已有当前页选择、批量确认、逐项 `If-Match`、幂等键重试、401/403 中止及部分失败反馈。

菜谱管理应复用这些规则和交互语义。不能为了“快速”改成浏览器直接逐行上传或出现半批数据。

来源：`backend/app/admin/catalog_csv.py`、`backend/app/admin/service.py`、`backend/app/admin/api.py`、`admin-frontend/src/features/catalog/`、`backend/tests/admin/test_catalog_csv.py`、`backend/tests/integration/test_catalog_draft_repository.py`。

### 5. 历史快照已有正确基础，新增候选状态不可破坏它

计划归档把 `PlanReport`、营养总量和 recipe provenance 写入 `DietPlanVersion`；目录后续失格不应改写已存版本。新增候选软删除、停用、更新必须只过滤新计划候选。候选记录若保留版本/删除时间，就能让归档继续读取生成当时的证据而不会依赖当前可用状态。

来源：`backend/app/planning/archive_service.py`、`archive_repository.py`、`archive_schemas.py`、`backend/tests/integration/test_diet_planning_agent_api.py`。

<recommended_architecture>
## 推荐实现边界

```text
管理员 CSV / 表格
        │ 公开 /api/v1/admin/*，实时 RBAC、原因、幂等、审计
        ▼
菜谱候选应用服务 ──► 候选 Repository ──► PostgreSQL
        │                         │
        │                         └─ 一对一引用已发布、合格 FoodCatalogItem
        ▼
PlanningService 候选查询/轮换/确定性营养计算/日校验
        │
        ▼
Agent tool adapter ──► DietPlanningGraph ──► 计划快照/用户 H5
```

### 候选资格

查询层必须同时证明：候选已启用且未删除、关联目录条目属于可用发布版本、营养四项齐全且合格、候选餐次匹配、固定份量可计算。候选不合格时 fail closed；不得用候选自身缓存的能量数字绕开营养目录。

### 轮换而非随机

选择策略应确定性地基于当前合格候选集和已经选择/近期使用的 recipe ID 排序：先排除本计划重复项和不满足偏好的项，再优先近期未使用候选；同一计划重试要使用同一请求/计划上下文以便审计与重现。随机数既不解决轮换，也让失败复现变差。

### 加餐的正确不变量

主餐集合固定为 `breakfast/lunch/dinner`。组合后仅在存在合格 `snack` 候选时尝试加入一项，随后运行同一整日校验；若失败，则丢弃该加餐并交付三餐，而非让可选加餐触发整份计划失败。归档和前端 DTO 的餐数应放宽为 3–4，并要求前三个固定有序、第四个只能是 `snack`。

### 导入与生命周期

菜谱 CSV 应以关联目录菜品名作为人填字段；服务在预览和确认时都做唯一解析，避免“预览时存在、提交时已停用”的竞态。建议输入的初始状态只允许`待审核`或`已停用`；启用是明确的、审计过的后台操作。软删除不物理删记录，不允许进入候选查询。

</recommended_architecture>

<implementation_risks>
## 主要风险与防线

| 风险 | 为什么会出问题 | 计划必须包含的防线 |
| --- | --- | --- |
| 把成品菜混入旧 `controlled_recipes` | 旧表和 DTO 强制项目自有配方、固定许可证、食材明细与三餐，放松约束会破坏审计语义。 | 分开管理员候选模型/端点；旧 seed 继续可读、可审计。 |
| 只给 `MealSlot` 加 `snack` | 所有 `len(MealSlot)`、归档 `max_length=3`、图反馈和 UI 映射都会把加餐误当必需或直接拒绝。 | 单独定义必需主餐与可选加餐，并在迁移、Schema、Graph、归档、UI、测试同次更新。 |
| 后台导入只校验 CSV 格式 | 名称可能未发布、重复或失格，导入后计划仍然空。 | 预览和确认均查目录资格；错误提供行号/字段，整批原子提交。 |
| 将“删除”做成物理删除 | 历史计划 provenance 外键/审计会丢失，无法解释旧计划。 | `deleted_at` 软删除；新计划过滤，历史快照保持。 |
| 用随机数换菜 | 难复现、重试可能不停抖动，审计也无法解释。 | 可复现轮换与近期使用规避；记录选择依据。 |
| 只隐藏后台按钮 | 普通用户仍可直接请求批量接口。 | 每个 API 进入 Service 后重新执行数据库当前管理员角色检查。 |

</implementation_risks>

<validation_strategy>
## 验证策略

1. **规划领域单测**：三主餐始终存在；符合条件的加餐才出现；加餐导致校验失败时退回三餐；候选按近期/已选规则轮换；任何目录不合格、停用、删除或偏好冲突的候选均不可选。
2. **后台服务单测**：CSV 表头/大小/行数、目录关联、重复名称、状态迁移、软删除、审计原因、幂等重试和全批回滚。
3. **真实 PostgreSQL 集成测试**：Alembic 升级，候选与目录资格联查，管理员/普通用户隔离，软删除后历史计划照常读取，新计划不再选中。
4. **Agent 图测试**：加餐的生成、替换和反馈槽位识别；重排上限和健康拒绝仍生效；Graph 只经 tool adapter 调 planning service。
5. **Admin React 测试**：新导航、表格、CSV 预览/确认、批量启用/停用/删除、401/403、冲突及重试。
6. **H5 React + Playwright + 内置浏览器**：真实管理员从登录到导入/启用；真实用户生成三餐和带加餐的计划，确认 H5 卡片与计划快照正确展示。

</validation_strategy>

## 计划切分建议

1. 候选持久化模型、Alembic、领域 Schema/Repository 与规划可选加餐不变量。
2. 管理员候选 CSV、Service/API、状态批处理、审计和真实 PostgreSQL 覆盖。
3. Agent 工具/图/归档与候选轮换、加餐反馈的端到端接线。
4. 后台菜谱管理前端、导航和批量交互；用户端计划卡片的可选加餐展示。
5. 教学文档、全链路测试、浏览器验收和既有 seed 迁移/兼容验证。

计划可按依赖关系将 1 作为基础波次，2 与 3 部分并行，4 在 API 合同明确后实施，5 收口。

## 结论

这是一次受控候选体系改造，而不是给现有页面再加一个菜单。最小正确路径是：以已发布营养目录为权威，管理员维护可启用的成品菜候选，规划服务从资格完整的候选池可复现地轮换组合，三主餐保持刚性、加餐保持可选，所有历史计划维持不可变快照。现有后台目录和计划归档已提供大部分安全骨架；真正的工作是把边界接对，而不是再造一套 CSV 或让模型自由编营养数。
